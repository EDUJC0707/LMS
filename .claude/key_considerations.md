# Key Considerations — 개발 내내 염두에 둘 설계 원칙

> 확정 스펙은 PRD가 기준. 이 문서는 **아직 스펙으로 굳지 않았지만 설계 시 반드시 염두에 둘 방향**을 모은다.
> 새 모델·API·화면을 만들 때 이 목록과 충돌하지 않는지 확인할 것.

## 1. Modularity — 기능은 모듈로, 노출은 상태로

- 모든 기능은 **켜고 끌 수 있는 모듈**처럼 설계한다. 화면·메뉴·API가 하드코딩된 고정 목록이 아니라, **서버가 내려주는 자격/부여 정보로 조립**되게.
- 이유: ① 상태 기반 노출 원칙(PRD §4 — 경쟁사 정찰 방지, 학생에겐 해당되는 것만) ② 대표의 직원 권한 부여 UI ③ 기능 단위 단계적 오픈(1차 범위 조정이 코드 수정 없이 가능해짐). 셋 다 같은 메커니즘 하나로 해결된다.
- 구현 함의: 소비자용 API 응답에 "이 사용자가 지금 쓸 수 있는 기능/콘텐츠" 정보를 포함시키는 계약을 처음부터 잡는다. 프런트는 그걸 렌더만.

## 2. 직원 권한 — 프리셋 + 개별 가감 (2026-07-22 확정)

- 기능 키는 코드가 정의(enum), 부여는 DB(직원↔기능키 매핑). 역할(관리자/조교)별 기본 프리셋 + 대표가 매트릭스 UI에서 가감.
- 강제는 API 레벨(퍼미션 클래스), 프런트 숨김은 보조.
- **대표 전용 민감 기능 범위는 추후 결정** — 후보로 논의된 것: 권한 부여 자체, 직원 계정 생성/비활성, 클리닉 컷값 변경·노쇼 영구제한 해제, 발송된 성적 정정 승인, 결제 취소/환불. → 구현 시 "대표 전용" 플래그를 기능 키에 둘 수 있게만 해두고 값은 비워둔다.

## 3. URL·앱 구조

- SPA 하나 + 경로 분리: `/student/*` `/parent/*` `/admin/*`. 로그인 3종 각 경로에. 같은 상위 도메인 + 세션 쿠키.
- 관리자 영역이 전체 개발 물량의 6할 이상 — 화면 20+. (디자인은 A/B/C 실험 결과로 결정, Carbon이 관리자 후보)

## 4. 추상화 경계 (교체 가능성 있는 것들)

- **영상 호스팅**: Provider 인터페이스로 감싼다. 업체(Mux/VdoCipher) 미정 + 연동 후순위. `videos` 도메인에 업체 종속 컬럼 금지.
- **결제**: 결제선생 → PG 전환 대비 Provider 추상화(PRD 6-5).
- **알림 채널**: 알림톡(솔라피 검토) → 앱 푸시 확장 대비 채널 추상화(PRD 6-8). 발송 시점 전체 리스트는 7/29 수신.
- **화상**: 구글 미트 API 계정 1개. 클리닉 1건 = 새 스페이스 1개(링크 재사용 금지).

## 5. 안전 기본값

- 노출 관련 기본값은 **닫힘**이다: 주차 게이팅(release 전 비공개), 자격 없는 기능 미노출, 신규 계정 bare.
- 파괴적 작업(퇴원·삭제·회수)은 자동화하지 않고 관리자 수동 + 이력.
- 수업 당일 현장 대응 불가 전제 — 모든 핵심 플로우에 수동 우회 수단(PRD §4 견고성).

## 6. 데이터 원칙 (설계 문서와 일치)

- 출결(attendances)이 SSOT — 복습영상 자동지급·클리닉 자격·리포트 대상이 전부 여기서 파생. 사본 금지.
- 상태·유형은 앱 레벨 값집합(한국어 TextChoices), DB CHECK 금지 — 값 추가 시 무마이그레이션.
- 큰 파일은 스토리지에, DB엔 경로만.
