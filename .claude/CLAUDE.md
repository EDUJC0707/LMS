# CLAUDE.md — 이 저장소에서 작업할 때의 규칙

한종철 LMS. React SPA(프런트) + Django/DRF/Celery(백엔드).

---

## 1. 저장소 구조 원칙 (가장 중요)

**작업 표면(우리가 매일 건드리는 것)은 넷뿐이다.**

| 경로 | 성격 |
|---|---|
| `backend/` | Django 앱·설정 |
| `frontend/` | Vite + React SPA |
| `infra/` | Dockerfile, fly.toml |
| `docs/PRD.md` | 제품 요구사항 — 살아있는 단일 기준 문서 |

루트의 설정 파일(`README.md`, `Makefile`, `docker-compose.yml`, `.gitignore`, `.dockerignore`)과 `.claude/`, `.github/`는 그대로 둔다.

이 규칙 파일 자체는 `.claude/CLAUDE.md`에 있다(루트 아님). Claude Code가 공식 지원하는 위치이며 `./CLAUDE.md`와 동일하게 로드된다. `.claude/`는 커밋 대상이다 — `.gitignore`에 넣지 말 것.

### 부가적인 것들은 작업 표면에 섞지 않는다

과거 작업물·리서치·프로토타입·에셋은 **성격별로 분류해 작업 표면 밖으로** 뺀다. `docs/`를 잡동사니 창고로 만들지 말 것 — `docs/`에는 개발 중 실제로 참조하는 것만 둔다.

성격 분류 기준:

- **살아있는 스펙** (계속 갱신) → 작업 표면에 유지 (`docs/PRD.md`, DB 설계)
- **완료된 결정·산출물** (불변 기록) → 아카이브
- **근거 리서치** (1회성 조사) → 아카이브
- **회의 원본·로그** → 아카이브
- **바이너리 에셋** (디자인 이미지 등) → 아카이브
- **프로토타입/실험 코드** → 아카이브 (예: 유튜브 권한 자동화 RPA는 "예전 testing" 성격)

`archive/`는 통째로 gitignore 대상이다 — 로컬 보관용이며 git에 올리지 않는다. 따라서 **아카이브로 옮긴 것은 백업이 되지 않는다.** 남겨야 할 기록이면 아카이브가 아니라 작업 표면에 둔다.

### 새 폴더를 즉흥적으로 만들지 말 것

작업 중 임시로 `report/`, `tools/`, `temp/` 같은 폴더를 만들어 두면 구조가 계속 어수선해진다.
새 산출물을 만들 때는 **위 성격 분류 중 어디에 속하는지 먼저 정하고**, 기존 위치에 넣는다.
폴더 하나에 항목이 1개뿐인 과잉 중첩(`tools/youtube-rpa/`)도 만들지 않는다.

## 2. 삭제·정리 규칙

- **삭제는 사용자 확인 후에만.** Claude는 삭제 후보를 **플래그**하고, 사용자가 확인하면 지운다.
- 지우기 전 **참조 검사**(grep)로 다른 파일이 그 파일을 쓰는지 확인한다. 특히 빌드 스크립트가 하드코딩 경로로 참조하는 경우가 있다.
- `rm -rf`는 없는 경로에도 성공을 반환한다. **삭제 후 실제로 사라졌는지 검증**할 것. 셸 작업 디렉터리가 어디인지도 확인(상대경로 사고 방지).
- git 미추적 파일은 지우면 복구 불가 — 커밋 여부를 먼저 확인한다.

## 3. 파일 이름 규칙

일회성 산출물·조사 문서는 **`YYYY-MM-DD-무엇을-했는지.md`** 형식으로, 날짜와 내용이 이름만 봐도 드러나게 한다.
같은 작업의 중간 버전은 남기지 않고 **최종본만** 유지한다.

## 4. 문서 이동 시

- 마크다운 상호 링크가 깨진다. 이동 후 **전체 링크 검증**을 돌린다.
- 빌드 스크립트의 상대경로(`path.join(__dirname, "..", ...)`)도 함께 고친다.
- PRD가 백틱으로 참조하는 경로도 갱신한다.

## 5. 절대 커밋하면 안 되는 것

- **RPA 크롬 프로필**(로그인 쿠키 포함) — `archive/` 전체가 무시되므로 함께 차단됨
- 대용량 디자인 원본 이미지 — 위와 동일
- `.env`, 시크릿

`.gitignore`는 **이미 추적 중인 파일에는 적용되지 않는다.** 규칙을 추가했는데 여전히 `git status`에 뜨면 인덱스에 들어가 있는 것이므로 `git rm -r --cached <경로>`로 빼야 한다(작업 파일은 남는다).

## 6. 문서 사실관계

PRD의 수치·결정은 **조사 근거 문서와 일치해야 한다.** 조사로 뒤집힌 사실이 PRD에 남으면 잘못된 설계로 이어진다.
(예: "유튜브 영상당 50계정 한도"는 2011년 옛 수치였고 실제는 약 32개 — 2026-07-17 사실검증으로 교정됨)

이미 뒤집힌 결정이 옛 문서에 남아 있으면, 그 문서를 그대로 두지 말고 **정정하거나 아카이브**한다.

## 7. 에이전트·워크플로 사용 제한

### 스킬은 항상 invoke, 절대 read로 대체하지 않는다

- 스킬(superpowers, hallmark, frontend-design 등)을 쓸 때는 **반드시 Skill 툴로 invoke**해서 지침을 로드한다. 스킬 파일을 Read로 읽고 흉내내는 것은 금지.
- 서브에이전트에 스킬 사용을 시킬 때도 프롬프트에 ①첫 행동으로 Skill invoke ②Read 대체 금지 ③보고에 invoke 증빙(로드 경로) 포함을 명시하고, 보고에서 증빙을 검수한다. 증빙 없으면 실패 처리.
- 서브에이전트에서 invoke가 안 되는 경우에만 메인 루프가 직접 invoke하고 이어서 진행한다.

- **에이전트는 20개 이상 동시에 launch하지 않는다.** 워크플로 1회 실행의 에이전트 총원도 20명 이하로 설계한다.
- 발견 건수에 비례해 에이전트가 늘어나는 구조(항목당 검증자 1명 등)는 금지 — 실행 전에 총원이 얼마가 될지 알 수 없기 때문. 검증은 **묶음당 1명**으로 배치한다.
- 총원을 미리 계산할 수 없는 작업이면 launch 전에 예상 규모를 사용자에게 말하고 진행한다.
- (사례: 2026-07-21 미팅↔PRD 대조 워크플로가 항목당 검증자 구조로 250명+까지 불어나 사용자가 중단시킴)

## 8. 소통

- 한국어로 답한다.
- 사용자는 장황한 설명보다 **결과와 판단**을 원한다. 옵션 나열 대신 추천을 제시한다.
- 확인이 필요한 결정은 **한 번에 모아서** 묻는다.
