## 2026-08-05 — 브랜치 6개를 main 으로 합침 (트랙 통합)

세션 6개가 각자 worktree 에서 일한 것을 한 번에 합쳤다. **worktree 는 전부 유지** —
합친 뒤 각 세션이 같은 자리에서 `git rebase origin/main` 하고 이어서 일한다.

순서는 "충돌을 줄이는 쪽" 이 아니라 **"깨지면 누구 때문인지 알 수 있는 쪽"** 으로 잡았다 —
하나씩 합치고 그때마다 전체 테스트를 돌렸다.
video → channeltalk → cookie-domain → notifications-sending → meet → omr.

### git 이 조용히 합쳐 놓고 런타임에 깨진 것 셋

병합 자체보다 **"충돌 없이 합쳐졌는데 돌리면 죽는" 것**이 문제였다. 셋 다 텍스트로는
충돌이 아니라서 git 은 성공을 보고했다.

- **`CELERY_BEAT_SCHEDULE` 이 두 번 대입됐다.** meet 은 `clinic-supervision`, notifications
  는 `retry-failed-notifications` 를 각자 **새로** 만들었다. 파일에 대입문이 둘이 되니
  나중 것이 앞의 것을 통째로 덮어 **알림 재발송이 조용히 사라졌다**(실측: settings 를
  읽으면 키가 `clinic-supervision` 하나뿐이었다). 한 딕셔너리로 합치고, 다음에 같은 일이
  나지 않게 "새 대입이 아니라 키를 더한다" 를 그 자리에 적었다.
- **`unique_id` → `matching_key` 개명이 뒤늦게 합쳐졌다.** omr 이 컬럼을 개명했는데
  meet·notifications 는 그 전에 갈라져 나가 `unique_id=` 로 학생을 만드는 코드를
  갖고 있었다. 줄이 달라 충돌이 안 났고, 합친 뒤 `TypeError`·`AttributeError` 가 됐다.
  프로덕션 3곳·테스트 6파일을 고쳤다.
- **`meet_url` → `conference_url` 도 같은 모양**이었다(seed·테스트). 다행히 이쪽은
  자동 병합 결과가 맞았다.

**교훈**: 브랜치끼리 비교해서 "충돌 없음" 을 확인한 것이 화근이었다. 실제로 봐야 할 것은
**브랜치가 더한 것이 main 의 현재 상태와 부딪히는가** 다. 마이그레이션 번호도 마찬가지로,
`accounts/0004` 가 main(로그인 시도 제한)과 omr(개명) 양쪽에 생겨 리프가 둘이 됐다 —
omr 것을 `0005` 로 밀고 `grades/0006` 의 의존을 따라 고쳤다(전부 순수 RenameField 라
데이터 위험은 없었다).

## 2026-08-05 — 로그인 시도 제한 · Sentry release · Cloudflare 판단

**아직 push 안 함**(영상 트랙과 함께 배포하기로). 커밋 `746ab9c`·`0759904` 가 로컬 `main` 에만 있다.

- **로그인에 시도 제한이 없었다.** 스로틀·axes·ratelimit 전부 0건이었고,
  우리 아이디는 **설계상 추측 가능하다**(`{이름}{번호4자리}`, 학부모 `{자녀아이디}p`).
  학생 이름만 알면 아이디의 대부분이 나온다. 위협 모델은 사용자가 명시했다 —
  *"other teachers might want to hack"*, 즉 아는 계정을 노리는 사람이지 무작위 봇이 아니다.
  - 한도 둘, **실패만** 센다(매일 로그인하는 학생이 제 발로 잠기지 않게):
    **계정별 10회/5분**(진짜 방어선 — IP 를 바꿔도 따라간다) ·
    **IP별 30회/5분**(한 곳에서 계정을 훑는 것. 학원이 공용 IP 라 넉넉해야 한다)
  - **검사는 `authenticate` 앞에서** 한다. 뒤에 두면 한도를 소진한 공격자가 다음 시도에
    비밀번호를 맞혔을 때 그대로 들어와 제한이 장식이 된다. 그 상황을 그대로 재현하는 테스트가 있다
  - **영구 잠금은 두지 않았다 — 잠금이 무기가 되기 때문.** 시험 전날 남의 아이디로 일부러
    실패시키면 그게 곧 우리 학생 대상 서비스 거부다. 창이 지나면 저절로 풀린다
  - 캐시가 아니라 `login_attempts` **표**에 쌓는다: 운영 웹이 gunicorn 워커 3개라
    프로세스별 메모리로는 셈이 3등분되고(한도 10 이 사실상 30), 배포가 잦아 메모리는 매번 날아가며,
    표적 공격 전제라면 **차단만이 아니라 흔적**이 남아야 한다
  - `X-Forwarded-For` 는 위조 가능하므로 **보조선인 IP 한도만** 그 값을 믿는다.
    위조로 얻는 것은 IP 한도 회피뿐이고 계정 한도는 그대로 걸린다.
    `REMOTE_ADDR` 을 쓰면 Fly 뒤에서 전원이 한 IP 로 묶여 IP 한도가 전체를 잠근다(테스트 있음)
  - 덤: 로그인 1건은 비밀번호 해시(PBKDF2 87만 회, 실측 229ms)가 비용의 거의 전부다.
    무제한 시도는 보안 구멍이자 **CPU 고갈로 서비스를 세우는 값싼 수단**이었다.
    검사가 앞에 있어 차단된 시도는 229ms 가 아니라 1ms 로 끝난다
  - 테스트 10건 · accounts+config 245건 통과

- **Sentry `release` 주입 완료.** `Dockerfile` 의 `ARG GIT_SHA` → `ENV SENTRY_RELEASE`,
  `prod.py` 가 명시적으로 넘긴다(SDK 가 환경변수를 알아서 읽지만 그 동작은 코드에서 안 보이고
  판올림에 딸려 바뀔 수 있다). **ARG 위치가 중요하다** — 커밋마다 바뀌는 값이라
  `uv sync` **뒤**에 둬야 의존성 레이어 캐시가 안 깨진다.
  넘기는 쪽은 CI(`github.sha`)와 `make deploy` 둘뿐 — **`fly deploy` 를 손으로 치면 태그가 조용히 사라진다.**

    입력창을 채우는 것은 `openChat` 의 셋째 인자다. 둘 다 부르게 고침
  - **메신저 언어가 브라우저 로케일을 따라갔다**(`36fed2d`). 번들 실측:

## 2026-08-05 — 알림 발송 파이프라인 (브랜치 `notifications-sending`)

- **발송 진입점 `queue()`** (`6f664f5`). 클리닉 출결·결석상담 종결 두 곳이 이미 `대기` 행만
