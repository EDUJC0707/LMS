# 알림 발송 시점 설계 (2026-08-11)

> **이 문서는 FLOW 3-11 로 대체됐다**(2026-08-12 대표 구술). 여기 15 시점은
> 코드 이벤트에서 기계적으로 뽑은 것이고, FLOW 는 그중 **"안 보내면 아무도
> 모르는 것" 8 가지**만 남겼다. 시점의 기준은 FLOW 다 — 이 문서는 8 이 어디서
> 왔는지의 근거로만 읽는다.

과거 발송분 8종(`local/sources/basis/alimtalk/samples.md`)은 **문체 참고용**이다.
발송 시점은 우리 시스템의 이벤트에서 새로 뽑는다 — 과거보다 많아진다.

**템플릿 개수 = 검수 리드타임 + 영구 유지비.** 묶을 수 있으면 묶는다.

## 2. 묶은 것과 그 이유

**3+4 성적 = 한 장.** 미응시는 점수 자리에 "미제출"이 들어갈 뿐 문서가 같다
(decisions §2 — 지각하면 OMR 이 안 들어와 미제출로 나가는 것이 설계된 동작).

**8+9 클리닉 대상·배정 = 한 장.** 둘 다 학생에게 가고, "신청하세요"와 "확정됐습니다"는
상태 문장 하나 차이다. 나누면 검수가 두 번이다.

**리포트를 따로 만들지 않는다.** PRD 3.1.2 의 "수업별 학부모 리포트"는 과거 문구에서도
성적 알림 한 통에 들어 있었다(점수 + 성적표 링크 + 과제 수행). `리포트` Type 은
남겨 두되 3번 템플릿을 쓴다 — 실제로 갈릴 이유가 생기면 그때 판다.

## 4. 값이 없어서 못 쓰는 문구

| 과거 문구 | 문제 | 판단 |
|---|---|---|
| "학생의 점수: `#{5}` / `#{7}점`" | 두 값이 뭔지 불명(등급? 원점수?) | **대표 확인** |
| "과제물 수행도는 `#{e}`" | 모델에 등급값 없음(`WorkbookSubmission` 은 제출 여부만) | **문단 삭제 권함** — 피드백은 워크북 지면에 있다 |

나머지 변수는 전부 있다 — 이름 `Student.user.name` · 시험일 `Exam.exam_date` ·
최고점 `Exam.max_score` · 클리닉 일시 `ClinicRequest.requested_date/requested_time` ·
링크 `conference_url` · 초기 비밀번호 `provisioning.generate_initial_password()`.

## 5. 코드 쪽 남은 것

- **본문 렌더링 층이 없다.** 지금 `queue()` 호출부가 `body` 를 안 넘긴다
  (클리닉 출결·결석 종결 둘 다 `title` 만). 알림톡은 본문이 승인 템플릿과 맞아야 해서
  빈 본문이면 거절된다. 유형별 문자열 템플릿 하나씩이면 충분하다 — 엔진 안 쓴다
- **10번 리마인더는 예약발송이 필요하다.** 알리고가 `senddate` + 취소를 지원하므로
  크론 없이 배정 시점에 한 번 건다. 단 취소하려면 업체 `mid` 를 들어야 하고,
  그건 `Notification` 에 **중립 참조 컬럼**이 필요하다(업체명 컬럼은 테스트가 막는다)
- **14·15 결제는 API 자체가 없다** — 결제선생 연동 스펙 대기

## 6. 순서

1. §3 죽은 규칙 고쳐 12장 문구 확정
2. §4 두 값 대표 확인
3. 알리고 등록 → 카카오 검수 (영업일 2~3일, 12장 한 번에)
4. 승인 코드를 `NOTIFICATION_KAKAO_TEMPLATE_CODES` 에
5. 렌더링 층 + 각 트리거에서 `queue()` 호출
