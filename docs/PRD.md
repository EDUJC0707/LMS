# LMS 구축 PRD (Product Requirements Document)

> **개정 이력**: 2026-07-15 방향확정 회의 반영(대규모 개정). 회의 전사·결정 로그는 `../local/sources/decisions/2026-07-15-lms-방향확정.md`, 변경 근거 45건은 동 문서 참조. 이번 개정으로 학부모 계정·출결관리·캘린더 홈·약점체크/문제은행·워크북 사진·상담기록이 신설되고, 일부 이전 결정(학부모 계정 범위, 영상 지급 방식, 랜딩 목적 등)이 변경됨. 확정 기술 스택은 9장 참조.

## 1. 개요

### 1.1 배경
현재 학원 운영 업무(성적 처리, 복습영상 제공, 교재 결제, 학생 상담, **출결 관리, 과제(워크북) 검사, 결석생 상담** 등)가 아카플로우, YouTube, 결제선생, 카카오톡, 자체 엑셀 등 서로 다른 외부 사이트/채널에 분산되어 있음. 이로 인해 관리자는 여러 시스템을 오가며 수작업(카카오톡 발송, YouTube 권한 수동 부여/박탈, 엑셀 출결 관리 등)을 반복해야 하고, 학생·학부모 입장에서도 정보 접근 경로가 통일되어 있지 않음.

### 1.2 목적
분산되어 있는 오프라인 제공 기능을 하나의 LMS 사이트로 일원화하여, 관리자의 반복 수작업을 줄이고 학생·학부모에게 단일 진입점을 제공한다. 나아가 대형 강의가 하기 어려운 **결석생 직접 관리**와 **시험 분석·약점체크 문항 제공**을 차별화 서비스로 제공하여, 설명회·홍보에서 오프라인 강의의 경쟁력으로 삼는다.

### 1.3 범위
- **포함**: 비로그인 랜딩 페이지(잠재고객 등록 전환), **로그인 후 통합 캘린더 홈**, 역할 기반 계정·권한 관리(**학부모 전용 계정 포함**), OMR 스캔본(PDF/jpeg) 인식·자동 채점 및 수동 보정, 성적 조회(분석·학습동선 포함), **출결 관리**, 복습영상 신청/수강(출석생 자동 지급), 결석 보강(동보), 클리닉 신청, **약점체크 유사문항 제공 및 문제은행(내신형/수능형 2종)**, **과제물(워크북) 검사 사진 업로드**, **상담 기록(결석·학부모)**, 교재 구매, 게시판(공지·질답·정오표·자유·이벤트/굿즈), 문의 기능의 웹 서비스화
- **제외(1차 범위 밖, 추후 검토)**: PG 직접 연동(현재는 결제선생 연동/임베드로 진행하되 추후 전환 가능하도록 설계), AI 기반 자동 학습분석(1년간 수기 축적 후 단계적 전환 — 3.1.8·6-18 참조)
- 참고: 클리닉 화상회의는 **구글 미트(Google Meet)를 유지**하되, 신청·배정·시간제한 링크 제공·입장 통제·녹음 관리를 LMS에서 담당 (6-3 참조)
- **변경 이력(OMR)**: OMR 채점은 당초 "외부 채점 결과 업로드"로 범위에서 제외되었으나, **스캔본(PDF/jpeg)을 LMS가 자체 인식 방식으로 자동 채점 + 수동 보정**하는 것으로 결정 변경 (결정 요약 6-1 참조)
- **변경 이력(클리닉)**: 클리닉 화상회의는 당초 "자체 WebRTC 배포"로 결정되었으나, **구글 미트 유지**로 변경 (결정 요약 6-3 참조)
- **변경 이력(학부모 계정)**: 학부모 전용 계정은 당초 "1차 범위 밖"이었으나, **1차 범위 포함**으로 변경 (결정 요약 6-2 참조)
- **변경 이력(랜딩)**: 랜딩 페이지 목적은 "강사 소개"에서 **잠재고객 등록 전환**으로 재정의 (결정 요약 6-10 참조)

## 2. 사용자 및 역할

| 역할 | 설명 |
|---|---|
| 대표 | 최상위 관리자. 전체 기능·권한 및 사용자 관리 |
| 관리자(운영자) | 학원 강사/직원. 성적 등록, 출결 입력, 영상 업로드, 수강 권한 관리, 결제 확인, 공지 게시, 상담 기록 등 운영 전반 담당 |
| 조교 | 관리자 보조. 부여된 범위 내 운영 업무 수행(워크북 사진 업로드, 클리닉 배정·수행 등). 권한은 관리자보다 제한적 |
| 등록생 | 1주차에 실제 출석하여 관리자가 '등록' 처리한 학생. 성적 확인, 캘린더 홈, 영상 신청/수강, 보강·클리닉 신청, 교재 구매, 문의 등 학생 기능 전반 이용 |
| 미등록(예비등록생) | 학원 출석부 명단에 올라 계정은 발급됐으나 아직 1주차 출석(등록) 전인 학생. **교재 구매만** 가능하고 그 외 기능은 미개방. 실제 출석 시 관리자가 '등록' 처리하면 등록생으로 전환 (3.1.5, 3.1.6, 6-9 참조) |
| 퇴원 | 수강을 이어가지 않아 관리자가 '퇴원' 처리한 학생. 기능 대상·리포트 발송에서 제외 (3.1.6, 8-6 참조) |
| **학부모** | 자녀(학생)와 연동된 **전용 계정 보유자**. 자녀의 성적·출결·결제 상태 **조회**(읽기 전용), 결석 동영상 보강(동보) 신청, 교재 결제, 상담/문의 신청 가능. 자녀 2인 이상이면 **자녀 선택 드롭다운**으로 조회 대상 전환. 성적·출결 등 데이터 수정 권한은 없음 (3.4, 6-2 참조) |

## 3. 주요 기능 요구사항

### 3.1 관리자 기능

#### 3.1.1 오프라인 성적 처리 및 성적표 배부
- **As-is**: OMR 수합 → 아카플로우에서 온라인 채점 → 카카오톡 알림톡 발송(개인성적·누적성적표 링크 포함) → 개인별 누적 성적표 인쇄 후 배부
- **결정 사항(변경)**: OMR 스캔(PDF/jpeg로 변환)까지는 사람이 수행하되, **LMS가 스캔본을 자체 인식 방식으로 자동 채점**하고, 스캔 시 발생하는 오인식·미인식에 대비한 **수동 보정 UI**를 함께 제공. 성적처리 완료 시 학생별 **약점체크 PDF(성적표 + 유사문항 다시풀기)가 자동 생성**되어 인쇄만 하면 되도록 함 (3.1.8 참조)
- **요구사항**
  - **OMR 인식·자동 채점**: 관리자가 스캔된 OMR 파일(PDF/jpeg)을 업로드하면 LMS가 **자체 인식 방식**으로 마킹을 인식하여 자동 채점
  - **수동 보정 UI**: 채점 완료 후, 해당 학생의 스캔된 OMR 카드 이미지와 인식된 답안을 **나란히 보여주고**, 오인식·미인식 문항을 관리자가 수동으로 수정할 수 있어야 함
  - **학생 식별·대조(원번 체계)**: 동명이인으로 인한 성적표 오배부를 막기 위해 학생마다 고유 식별번호(원번, `unique_id`)를 부여
    - 원번(`unique_id`) = **숫자부만**: 학년(1자리) + 전화번호 뒷 4자리 = **총 5자리** (예: `3_1234`). **이름은 원번에 포함되지 않는 별도 항목**이며, 성적표 대조는 **원번과 이름을 함께** 사용함
    - 원번은 **단독으로는 중복될 수 있으므로** 이름과 함께 쓰는 **매칭 키**로 사용 — 시스템 내부 식별은 별도의 고정 식별자를 사용
    - **원번 고정(불변)**: 원번은 **최초 발급 값으로 고정**되며, 이후 학생이 전화번호를 바꾸더라도 원번은 변경되지 않음
    - 학년 코드: `1`, `2`, `3`, `4 = 재수생`
    - **정상 매칭**: OMR에서 인식된 원번과 이름이 **모두 일치**하는 학생이 DB에 유일하게 존재하면 해당 학생 정보로 자동 입력
    - **부분 인식(이름·원번 중 하나만 인식)**: 인식된 값에 해당하는 학생이 DB에 **하나뿐이면 자동 처리**, **둘 이상이면 관리자가 확인·선택**
    - **이름·원번 불일치 / DB 미존재 / 인식 비정상 / 원번 중복**: 각각 경고를 표시하고 관리자가 확인·수정·지정할 수 있는 UI 제공
    - **학급(반) 이동 대응**: 등록 학급과 채점 학급이 달라도 **원번·이름 기준 대조**로 오배정·누락 방지 (학급 정보는 매칭 키로 사용하지 않음)
  - **마킹 이상 경고**: 무응답, 복수 마킹 등 마킹 이상을 관리자가 확인할 수 있도록 경고 표시
  - **OMR 추가 마킹란('더 풀고 싶은 문항')**: OMR 카드의 각 문항번호 옆에 추가 마킹용 색칠 박스를 두고, 학생이 정오와 무관하게 추가 학습을 원하는 문항을 마킹함. LMS는 이 마킹란도 인식하여, **[틀린 문항] + [학생이 추가 마킹한 문항]** 각각에 유사문항을 제공(3.1.8 참조). 손글씨가 아닌 마킹이라 인식 정확도가 높음
  - **문항 정보 입력(채점 기준)**: 관리자가 시험별로 각 문항의 **정답, 배점, 대단원, 중단원, 테마 태그, 오답 시 학습 가이드, 내신형/수능형 구분**을 LMS에 입력할 수 있어야 함
    - **오답 시 학습 가이드**: 각 문항에 "이 문항을 틀렸을 때 무엇을 학습해야 하는가"(관련 복습영상/강의 차시, 개념서 페이지·단원, 학습 코멘트 등)를 함께 입력. 오답 학생의 성적표에 학습동선으로 노출됨(3.2.1). 초기에는 전량 수기 입력하여 향후 AI 분석용 데이터로 축적(6-18)
    - **테마 태그**: 누적 테마별 정답률(3.2.1) 및 약점체크의 집계 축. (테마 정의는 미결 — 8-7 참조)
  - **성적표 공지사항 입력**: 성적표 출력(배부) 전에 관리자가 성적표에 표시될 공지사항을 입력할 수 있어야 함
  - 채점·보정이 완료된 성적은 자동으로 학생별 누적 성적표에 반영되어야 함
  - 성적 등록 완료 시 학생·학부모에게 알림(카카오톡 알림톡 또는 자체 알림) 발송
  - 성적표는 인쇄용 포맷(PDF 등) 출력을 지원해야 함
  - **수업별 학부모 리포트 알림**: 매 수업이 종료되기 전에, 해당 수업 **출석 학생의 학부모**에게 당일 성적표·누적 성적·과제 수행 여부를 알림으로 전송
    - **발송 대상(출석생)**: **DB에 입력된 출석생 전원**(담임이 성적처리 워크플로우 중 입력한 실제 교실 출석 기준 — 별도의 '시험 응시자' 개념은 두지 않음. **출결 입력은 3.1.6 참조**)
    - **시험 미응시 출석생 처리**: 출석했으나 미응시한 학생은 **성적표를 생성하지 않고** 리포트에 **'성적표 없음'**으로 표기, 당일 시험은 **0점(미응시)**. 과제 수행 기록은 관리자가 수동 입력
    - **과제 수행 여부 표기 규칙**: 미수행이면 **'미수행'**, 수행이면 업로드된 **워크북 사진 링크**를 포함(클릭 시 워크북 마지막 페이지 이미지 열람 — 3.1.7 참조)
    - **발송 후 성적 수정 가능**: 오발송·오채점 대비, 알림 발송 이후에도 성적 정보 수정 가능
    - **개인별 발송**: 전체 일괄 발송뿐 아니라 특정 학생 1명 단위 (재)발송 가능

#### 3.1.2 알림 발송
- **결정 사항(채널 추상화)**: 알림은 "알림 채널" 인터페이스로 추상화. **현재는 카카오 알림톡**을 사용하되, 향후 자체 앱 푸시 등으로 확장·교체 가능하도록 설계 (6-8 참조)
- **요구사항**: 성적 등록, 영상 권한 부여, 결제 완료, **수업별 학부모 리포트(당일 성적표·누적 성적·과제 수행 여부[워크북 사진 링크])**, **클리닉 대상 여부(2026-07-15 회의 — 판정 확정 즉시 대상자에게 신청 안내 발송)**, 클리닉 출결, 동보 처리, 노쇼 경고, 상담 안내 등 주요 이벤트 발생 시 알림 발송. **발송 시점 전체 확정 목록은 미결 8-17(2026-07-29 전달 예정)**
  - 전체 일괄 발송과 **개인별(학생/학부모 1명 단위) 발송**을 모두 지원
  - 알림 발송 이후에도 성적 정보는 수정 가능 (3.1.1 참조)
  - **발송 내역 조회**: 발송 대상·채널·발송시각·전달 상태(성공/실패)를 관리자가 조회·확인
  - **참고(운영)**: 결석생 전화 상담의 통화 횟수 집계·문자 발송 등은 상용 서비스(예: 채널톡) 연계를 검토 (9.2 참조)

#### 3.1.3 영상 업로드
- **As-is**: YouTube에 비공개(Private)로 업로드
- **결정 사항(2026-07-21 회의 — 방식 전환 확정)**: **YouTube + RPA 봇 방식 폐기, 외부 DRM 영상 호스팅으로 전환 확정.** RPA는 개발 완료·동작 확인됐으나 유튜브 측 코드 변경 시 작동이 수시로 멈추는 문제가 확인되어 안정성 사유로 폐기. 업체는 **Mux/VdoCipher 중 미정** (`../local/sources/decisions/2026-07-20-외부서비스-결정.pdf` 기준으로 선정)
  - **화질: 4K 확정** — 시청량 추정(월 1,200~1,500시간) 기준 추가 비용이 월 약 17만원 수준이라 감수 (6-7 비용 전제 참조)
  - **연동 개발은 후순위** — 1차 개발은 이 부분 없이 착수하고, 영상 도메인은 호스팅 Provider 추상화로 설계해 연동 시점에 구현체만 붙인다
- **요구사항**: 관리자가 복습영상을 업로드하고 강의/차시 단위로 분류·관리. 시청은 **LMS 내 임베드 재생**(DRM으로 다운로드·링크 유출 차단), 시청 권한은 지급/만료에 따라 **API로 자동 부여·회수**
  - **보관 정책**: 영상은 1월~11월 초 종강까지 **삭제 없이 전량 누적 보관**(주 3교시 × 32주 = 연 최대 약 96~100시간, 시즌 종료 후 아카이브 — 8-16 결정)
- **폐기된 구 방식 참고**: 유튜브 비공개 + 계정별 권한(약 32계정 한도, 8-2), 학생 구글 계정 수집, 별도 PC RPA 봇 — 전부 2026-07-21 폐기. DB의 `youtube_email` 등 유튜브 종속 컬럼은 연동 설계 시 정리

#### 3.1.4 영상 수강 권한 지급
- **As-is (상세)**: 신청자 구글 이메일 수령 → 비공개 유튜브 영상을 해당 계정에 공개 전환 → 부여 내역 엑셀 정리 → 수강 기간 경과 후 다시 비공개. 전 과정 수동
- **결정 사항(변경 — 출석생 자동 지급 분기 신설)**: 복습영상 지급 경로를 **출석 트리거(자동)** 와 **신청 기반** 으로 분기한다.
  - **① 복습영상(출석생 자동 지급)**: 담임의 출결 입력(3.1.6)에서 그 주 **출석으로 확정된 학생**은 **학생 신청·관리자 승인 절차 없이** 그 주 복습영상 수강 대상으로 **자동 등록**된다. LMS는 출석 확정 즉시 대상 등록·부여 지시(할일)·안내·만료 이력을 자동 처리한다. (기존 3.2.2의 신청 기반 플로우를 거치지 않음 — 6-4 변경)
  - **② 결석보강(동보)·예외**: 결석생 동보는 3.2.3의 관리자 '동보' 체크(또는 연락 두절 시 학생·학부모 신청)로 지급한다.
  - 실제 시청 권한의 부여/회수는 외부 DRM 호스팅 API로 자동화한다(3.1.3, 연동은 후순위). LMS는 **대상 산정·부여·안내·만료 관리**를 담당하며 이 로직은 호스팅 방식과 무관하게 먼저 개발 가능하다.
- **요구사항 (간소화 플로우 — 신청 기반 케이스)**:
  1. **신청**: 학생이 LMS에서 신청
  2. **자격 확인·승인**: LMS 자동 확인 또는 관리자 수동 승인/거절
  3. **권한 부여**: 승인 시 해당 학생 계정에 시청 권한 부여(호스팅 API 자동 — 연동 전에는 관리자 수동 처리)
  4. **안내**: 권한 부여 후 학생에게 알림 안내(LMS 시청 페이지 링크 포함)
  5. **시청**: 학생이 LMS 내 임베드 플레이어로 시청
  6. **만료**: **시청 기간은 지급일로부터 7일(2026-07-15 회의 — 기본값, 관리자 설정으로 변경 가능)**. 기간 종료 시 시청 페이지 자동 소멸 + 권한 자동 회수
  - 수동 권한 부여/회수(예외 처리)도 가능
  - **부여·만료 이력 관리**: 학생별 부여일·만료 예정일·회수 여부를 LMS가 기록·추적

#### 3.1.5 교재 결제 내역 확인
- **As-is**: 학원으로부터 등록생 명단/연락처 수령 → 카카오톡 청구서 발행(결제선생) → 결제내역 확인 후 배부. (청구서를 일일이 발송, 확인 인원 다수, 외부 프로그램 다수로 학부모가 어려워함)
- **결정 사항(변경)**: 결제선생을 LMS에 연동/임베드하되, **학생과 학부모 양측 모두 교재 결제를 개시·완료할 수 있다.** 중복 결제를 방지하기 위해 동일 학생·동일 교재에 대한 청구/결제 상태를 양측 경로 간 **동기화(sync)** 한다. 교재 청구는 **커리큘럼(약 10주) 시작 첫 수업 기준으로 1회** 발송(주차별 반복 아님). 학원의 유일한 과금은 이 교재 결제이며 별도 수강료는 없음. (향후 PG 직접 연동 전환 가능성을 열어두고 설계)
- **요구사항**
  - 학생 또는 학부모가 교재 구매를 희망할 때 **버튼 클릭만으로 청구가 시작**되어야 함
  - **양측 결제 및 중복 방지(sync)**: 학생 버튼 트리거 청구와 학부모 측 결제가 모두 가능하되, 동일 학생·동일 교재에 대해 청구/결제가 한 번 성립하면 다른 경로의 청구서 발송을 자동 차단
  - **중복 청구 방지 플래그(내부 캘린더 연동)**: LMS 내부 교재 스케줄/캘린더에 각 교재별로 「이미 청구 발송되었는지」 플래그를 두고, 어느 경로에서 요청이 와도 중복 발송하지 않음
  - **청구 시점(첫 수업 기준)**: 정기 주차 청구가 아니라 해당 교재가 사용되는 첫 수업 시점 기준으로 발송
  - 관리자가 학생별 교재 구매/결제 상태(완료·미결제·배부)를 조회
  - 결제 상태는 결제선생 데이터를 LMS와 동기화하여 반영
  - **설계 시 고려사항**: 결제 로직을 "결제 제공자(Provider)" 인터페이스로 추상화하여, 추후 결제선생 → PG 교체 시 주변 기능 변경 없이 구현체만 교체 가능하도록 설계
  - **신규생 계정 자동 발급·발송**: 신규생은 교재 구매 가능 시간이 극단적으로 짧으므로, **등록생 명단이 입력되면 출석일 하루 전에 계정이 자동 생성·문자(SMS) 발송**되어야 함
    - **학생·학부모 계정**: 아이디·초기 비밀번호를 연구실에서 **일괄 생성 → 문자(SMS) 발송 → 최초 로그인 후 비밀번호 변경**. **아이디 = 본인 휴대폰 번호**(2026-07-21 확정 — 8-4. 휴대폰 없는 학생은 학부모 번호 기반 예외, 발송도 학부모 연락처로 — 8-3). 비밀번호는 랜덤 생성·변경 가능
  - **등록 상태 관리**: 명단 입력 시 계정 발급 학생은 전원 **미등록(예비등록생)** 상태로 교재 구매만 가능. **1주차에 실제 교실에 출석한 학생**을 관리자가 **'등록' 처리**(3.1.6)하면 등록생으로 전환되어 전체 기능 개방
  - **권한 분류(RBAC)**: 대표·관리자·조교·등록생·미등록·퇴원·**학부모** 역할에 따라 기능 접근 제어 (2장, 6-9 참조)

#### 3.1.6 출결 관리 (신설)
- **As-is**: 담임이 매 수업 출석/결석을 별도 엑셀로 관리 → LMS와 분리되어 복습영상 권한 부여·클리닉 대상 선정·성적표 발송 대상 산정에 수기 대조가 필요했음
- **결정 사항**: 회차별 출결(출석/결석)을 **엑셀에서 LMS로 이관(엑셀 폐기)**. 담임이 당일 OMR 리딩·성적처리를 마친 뒤 워크플로우의 일부로 LMS에서 각 학생의 출석/결석을 직접 입력·수정. 이 출결이 **복습영상 자동지급·클리닉 대상 판정·캘린더 도장·학부모 리포트 대상의 단일 원천(SSOT)** 이 됨
- **요구사항**
  - **출결 입력(담임)**: 담임이 수업 회차별로 학생 각각의 출석/결석을 LMS에서 직접 입력·수정
  - **출결의 단일 원천**: 여기서 입력된 출석 값이 (1)수업별 학부모 리포트 발송 대상(3.1.1), (2)그 주 복습영상 자동 지급(3.1.4), (3)클리닉 대상 판정 전제(3.2.4), (4)캘린더 홈 출결 도장(3.2.0)의 공통 기준. '시험 응시 여부'는 출석과 **별개 속성**으로 관리(미응시 처리는 3.1.1)
  - **출석 → 복습영상 자동 지급(트리거)**: '출석' 학생은 별도 신청·승인 없이 그 주 복습영상 수강 대상으로 자동 등록 (3.1.4 ① 참조)
  - **출석·응시 → 클리닉 대상 전제(트리거)**: 클리닉 대상 판정의 전제는 "출석 + 현장 시험 응시"이며, 결석생·미응시자는 제외 (평균 미달 조건 및 활성화는 3.2.4)
  - **출결 → 캘린더 도장(트리거)**: 출석일=출석 도장, 결석일=결석 도장으로 캘린더 홈에 노출(3.2.0). 3.1.6은 데이터 원천을 제공
  - **학생·학부모 동일 노출**: 학생·학부모가 각자 계정에서 회차별·누적 출결을 동일하게 조회
  - **퇴원 처리**: 수강을 이어가지 않는 학생을 담임/관리자가 출결 관리 화면에서 **퇴원 처리**할 수 있어야 함. 퇴원 학생은 이후 출결·성적·영상 대상 및 학부모 리포트 발송에서 제외 (퇴원은 학생 생애주기 상태로 관리 — 회차별 출결과 분리. '등록 안 한 학생' = 1주차 미출석 등록 미전환자, 자동 퇴원 없이 관리자 수동 처리 — 8-6 결정)

#### 3.1.7 과제물(워크북) 검사 사진 업로드 (신설)
- **배경**: 조교가 워크북(학생 책) 마지막 페이지에 수기 코멘트·수행도 ABC 도장을 남기지만, 학생 책이라 학부모가 확인할 수 없음. 워크북은 책 마지막 페이지여서 OMR(A4 단면)처럼 스캔 리딩이 불가 → 사진 촬영으로 디지털화
- **요구사항**
  - 조교가 워크북 마지막 페이지를 촬영한 사진(수기 코멘트 + 수행도 ABC 도장 포함)을 업로드하면 해당 학생 레코드에 매핑되어 저장 (매핑 방식은 아래 원번 OCR — 8-9 결정)
  - **원번 기입칸(워크북 지면 인쇄 사양, 1개)**: 워크북 마지막 페이지에 원번(`unique_id`, 5자리) 기입칸을 인쇄한다. **기입 주체는 학생이 아니라 조교**(2026-07-15 회의 — 인식률 확보 목적). 시스템은 이 칸을 **OCR로 인식해 사진을 해당 학생에게 자동 매핑**하고, 인식 실패 시 관리자가 수동 지정으로 보정
  - **코멘트는 텍스트 변환 불필요**: 수기 코멘트는 OCR 대상이 아니며, 사진 이미지 자체를 학부모·학생에게 그대로 보여준다(별도 정서 입력칸 없음 — 2026-07-15 회의)
  - 수기 코멘트 + 수행도 ABC 도장 방식은 유지(학생 선호)
  - 업로드 사진은 3.1.1 학부모 리포트의 '과제 수행 여부'(사진 링크)로 연결
  - **당일 운영 순서**: 조교의 워크북 채점·사진 업로드는 학부모 리포트 문자 발송의 선행 작업. 업로드 누락 시 개인별 (재)발송으로 보정

#### 3.1.8 약점체크 유사문항 제공 & 문제은행 (신설)
- **목적**: 모든 시험(미니테스트·모의고사·교육청·평가원·학교시험)에 대해 틀린 문항의 유사문항을 자동 제공하여 약점 보완용 '다시풀기' 자료를 배부. (대표가 정리한 핵심 차별화 2가지 중 하나)
- **요구사항**
  - **문제은행 2종 분리**: ①**내신형(개념확인)** 문제 DB, ②**수능형** 문제 DB. 내신형 = 미니테스트 약점체크·워크북 자료용, 수능형 = 모의고사 분석 후 약점체크용. 유사문항 조회 시 원 시험 유형에 대응하는 DB에서 조회
  - **유사문항 사전 매칭**: 문제 원고 작성 단계에서 각 문항당 **유사문항 2개**를 사전 매칭(1개는 보강 효과가 약하다는 판단). 매칭 결과는 문제은행에 저장되어 채점 후 자동 조회에 사용
  - **문항 라벨링**: 문항 라벨링 툴에 '내신형/개념형' 체크 컬럼 및 난이도 등 세부 라벨을 추가. LMS는 이 라벨을 기준으로 오답·추가마킹 문항의 유사문항을 조회·연결 (라벨링 툴이 LMS 내부 기능인지 외부 도구인지는 논의중)
  - **자동 조회·제공 대상**: OMR 채점 완료 후 **[틀린 문항(기본)] + [학생이 OMR 추가 마킹란에 표기한 문항]** 각각에 유사문항 2개씩 제공
  - **학생별 약점체크 PDF 자동 생성**: 성적처리 완료 시 학생별 PDF가 자동 생성되어 관리자는 인쇄만 함. 구성 = **1페이지 성적표** + 이후 페이지 **'문항 다시풀어보기' 2단(2컬럼) 양식**에 유사문항 자동 삽입. 표지에 학생 이름을 표기하여 조교가 이름순 정렬·배부
  - **범위**: 온라인 실시간 풀이 시스템이 아니라 **오프라인 인쇄 배부**로 한정(학생이 종이로 다시 푼다)
  - **학습분석 단계적 전환(로드맵)**: 문항별 학습진단·학습방향(3.1.1) 및 유사문항 매칭은 초기(약 1년) 전량 수기 입력·축적 → 데이터 확보 후 AI 기반으로 단계적 전환. 데이터 스키마는 초기부터 AI 활용 가능한 구조(문항–테마–오답–학습방향 매핑)로 설계 (6-18)
  - **리스크**: 시중 문제집 수록의 저작권(오프라인 배포·비판매라 낮다고 판단하나 법적 검토 필요), 라벨링 품질 의존

#### 3.1.9 상담 기록 (신설, 관리자용)
- **결정 사항**: 결석생 전화 상담 및 학부모 상담 신청 내용을 LMS에 기록·관리 (핵심 차별화 1 — 결석생 직접 관리)
- **(1) 결석 상담 기록**
  - 출결에서 '결석' 처리된 학생을 **상담 대기열**로 자동 제시
  - 결석 담당자가 학생별 상담 카드를 작성: 통화 대상(학부모/학생), 통화 일시, 결석 사유, **동보(동영상 보강) 신청 여부**, 통화 내용 메모, 후속 조치(오프라인 콘텐츠 제공·학습 대응 방안 제안)
  - **통화 순서 정책**: 당일(늦어도 다음날)까지 **학부모 1차 → 미해결/필요 시 학생 2차**. 학생 통화는 즉각이 아니라 통화 가능 시간대(예: 저녁 이후)
  - '동보 신청 여부'가 체크되면 영상 지급 플로우(3.2.3)로 연계
  - 상담 기록은 관리자만 열람
- **(2) 학부모 상담 기록**: 학부모가 신청/요청한 상담 내용(신청 일시, 대상 자녀, 요청 내용, 처리 상태[접수/진행/완료], 관리자 응답 메모)을 기록·관리. 열람은 관리자 전용

### 3.2 학생 기능

#### 3.2.0 로그인 후 캘린더 홈 (신설, 첫 화면)
- **결정 사항**: 학생·학부모 모두 로그인 직후 첫 화면으로 **통합 캘린더 홈**을 제공. 게시판 글을 일일이 클릭하던 올드한 구조를 지양하고, 출결·커리큘럼·오늘 할 일·과제를 캘린더 한 화면에서 확인
- **요구사항**
  - **대상**: 학생·학부모 동일 화면. (학부모는 자녀 2인 이상 시 자녀 선택 드롭다운 기준으로 표시 — 3.4)
  - **출결 도장**: 출석일=출석 도장, (와야 하는데 안 온) 결석일=결석 도장으로 누적 출결을 달력으로 표시 (원천 3.1.6). '와야 하는 날' 판정은 학생별 반 스케줄에 의존
  - **주차별 커리큘럼**: 강좌의 주차 구분(예: 로직엔제 1주차, 2주차 …)을 표기
  - **주 단위 학습계획**: 특정 주에 커서를 올리면(호버) 그 주 1일 단위 학습계획(Day1, Day2 …) 표시 → 게시판에 들어가지 않아도 확인. (**터치 환경[아이패드·모바일]은 호버 불가 → 탭/펼치기 등 대체 인터랙션 필수** — 반응형 4장)
  - **오프라인 특이사항(주차 공지)**: 해당 주차 특이사항을 캘린더에 표기(예: 로직엔제 1주차=오메가블랙 1회 응시). 공지사항 게시판(3.3.1)과 연동
  - **정보 집약 범위**: 전체 커리큘럼 진행·오늘 할 일·과제·출결을 한눈에 제공하고, 학부모 관점에서는 결석·동보 신청 여부 및 교재 결제(3.1.5) 상태까지 확인(동보 학생의 영상 수강률·진도율 표시는 UI 복잡도 사유로 보류 — 2026-07-15 회의).
  - **상태 기반 노출**: 캘린더 홈을 포함한 모든 소비자 화면은 §4 "상태 기반 노출 원칙"을 따른다 — 커리큘럼·학습계획·공지는 시작된 주차까지만, 기능(동보·클리닉 등)은 자격이 있는 학생에게만 등장. 단 **UI 과복잡 지양** — 마감 임박 항목(클리닉 시간·영상 만료·결제 기한)을 우선 노출하는 우선순위 기반 배치. 반영대기목록의 '오늘 놓치면 안 되는 것' 카드를 본 캘린더 홈에 통합

#### 3.2.1 누적 성적표 확인
- **결정 사항(성적표 개편)**: 기존 아카플로우 성적표의 낮은 가독성을 개선하기 위해 성적표를 **새 포맷으로 재설계**(구체 레이아웃은 담당 개발자 설계). 점수·통계 나열에 그치지 않고 **앞으로의 학습 방향을 제시하는 분석 자료**를 포함. 성적표는 학생·학부모 모두 열람 가능
- **성적표 구성(최소 포함 항목)**
  - **학생 정보**: 성명, 인식번호(원번), 학교, 시험 날짜, 시험명
  - **공지사항**: 성적표 출력 전 관리자가 입력한 공지사항
  - **성적 요약**: 내 점수/만점, 전체 평균, 표준편차, 최고점, 상위 30% 점수, 백분위
  - **대단원별 점수**: 대단원별 문항 수 / 정답 수(틀린 수) / 내 점수(및 단원 만점) / 내 정답률
  - **문항 채점표**: 각 문항의 번호, 단원, 배점, 정답, 채점 결과, 오답률
  - **성적 현황(회차별 추이)**: 회차별 본인 성적, 백분위, 전체 평균, 상위 30% 점수, 전체 최고점
  - **오답 문항 학습동선(신설)**: 틀린 각 문항에 대해 출제 시 입력된 '오답 시 학습 가이드'(3.1.1)를 함께 표시하여 다음 학습 행동(복습영상 시청/개념서 복습 등) 안내. (틀린 문항이 없으면 표시하지 않음)
  - **테마별 누적 정답률 추이(신설)**: 각 문항에 입력된 '테마'(예: 중화반응 등)를 집계 축으로, 회차가 누적됨에 따른 테마별 정답률 변화를 표·그래프(예: 꺾은선)로 제공. 특정 테마의 강·약점과 시간에 따른 향상/정체/하락을 파악 → 학생 자기진단·상담 자료로 활용. (테마 정의는 미결 8-7)

#### 3.2.2 복습영상 수강 / 3.2.3 결석생 동영상 보강(동보) 신청
- **결정 사항(변경 — 6-4 통합 플로우 폐기)**: 복습영상과 결석보강은 지급 경로가 분리된다. 신청 유형(복습영상/결석보강) 카테고리 구분은 조회·이력 목적으로 유지
- **3.2.2 복습영상(출석생 자동 지급)**
  - 담임의 출결 입력에서 그 주 **출석으로 확정된 학생**은 **학생 신청 없이** 그 주 복습영상 수강 권한을 자동 지급받는다 (3.1.4 ①, 3.1.6). 학생이 별도로 신청·선택하는 대상은 결석보강(동보)에 한한다
  - 학생은 **LMS 내 임베드 플레이어로 시청**(외부 DRM 호스팅 — 3.1.3, 연동 전 임시 운영은 관리자 수동). 시청 기간(기본 7일) 종료 시 시청 페이지 자동 소멸(3.1.4)
- **3.2.3 결석보강(동보)**
  - **동보 정의**: 결석생이 결석 사유 확인 전화상담(3.1.9) 후 "집에서 영상으로 보강하겠다"고 확정한 경우
  - **1차 경로(관리자 체크)**: 관리자가 상담 후 해당 학생에게 LMS에서 **'동보'를 체크**하면, 즉시 그 주 출석생과 **동일한 복습영상 권한**을 자동 부여(권한 부여 방식은 3.1.3·6-7)
  - **예비 경로(연락 두절)**: 전화상담이 닿지 않은 결석생은 LMS 로그인 후 **'동보 신청' 버튼**으로 직접 신청. 관리자가 목록을 확인해 지급. **동보 신청은 학생 본인과 학부모 모두 수행 가능**
  - **과금 없음(2026-07-15 확정)**: 동보에는 별도 수강료가 없다. 학원 과금은 커리큘럼(약 10주) 수강생의 교재 1회 결제(결제선생, 3.1.5)뿐이며, 동보는 이미 결제한 수강생에게 결석분 영상을 제공하는 것이므로 추가 청구하지 않는다

#### 3.2.4 클리닉 신청
- **As-is**: 카카오톡 채널로 신청 접수 → 승인 완료 알림톡(구글 미트 링크 동봉) → 정해진 시간에 진행
- **결정 사항(변경/구체화)**: 클리닉은 **구글 미트 유지** 1:1 과외. 신청·배정·링크 제공·입장 통제는 LMS. **대상자(자격)를 게이팅**하고 시간대를 **정해진 슬롯**으로 운영
- **요구사항**
  - **클리닉 대상자(신청 자격)**: 아래 세 조건을 **모두** 충족한 학생에게만 신청 활성화 — ① 해당 시험일 **출석**, ② 현장에서 **시험 응시**, ③ 해당 시험 성적 **평균 미달**. 단순 출석·시험 미응시자·결석생은 대상 아님
  - **대상자 판정·신청 활성화**: 관리자가 해당 시험의 평균(기준)을 입력하면 대상자를 판정. 각 학생 화면에 대상자는 **활성화된 '신청' 버튼**, 비대상자는 **'미대상자'(비활성)** 표시. (평균 미달 기준=전체평균 자동 vs 별도 컷값은 미결 8-10)
  - **시간대(정해진 슬롯) 선택**: 시간대는 **월~금**의 사전 정의된 슬롯(예: 7~8시/8~9시)으로 제한, 학생이 원하는 슬롯을 **버튼 클릭으로 신청**. 요일·슬롯·정원은 관리자가 설정
  - **정원·마감(신청 차단)**: 슬롯 정원은 해당 시간대에 배정 가능한 **조교 수 기준**으로 관리자가 설정(2026-07-15 회의). 활성 신청 수(대기+승인)가 정원에 도달한 슬롯은 **신청 버튼 비활성(마감 표시)** — 현재 수기로 다른 시간대를 안내하던 것을 시스템이 차단·안내
  - **신청 수정·취소**: 신청 후 시간 수정 및 **버튼으로 취소** 가능(취소는 노쇼로 집계하지 않음)
  - **당일 신청 마감(오전 8시)**: 당일 오전 8시 이후에는 해당 날짜의 클리닉 신청·변경 불가
  - 관리자가 배정 가능 직원 확인 후 **승인+배정(담당 직원 지정)** 또는 미승인. 학생은 상태(대기/승인·배정완료/미승인) 조회
  - **시간 제한 링크 제공**: 배정된 구글 미트 링크는 **신청 시작 5분 전부터** 해당 **학생 계정에만** 노출
  - **녹음(감독용, 녹화 아님)**: 조교가 클리닉을 정상 수행했는지 감독하기 위한 녹음만 제공
  - **조교 수행 평가표**: 관리자가 평가 항목을 미리 입력하고, 녹음본 근거로 조교 수행을 평가·기록
  - **출석/결석 알림(진행 중 발송)**: 조교가 **출석 처리 버튼**을 누른 순간 학부모에게 출석 알림 발송. 시작 시간으로부터 **10분 이상 미출석 시 결석 처리 버튼**으로 결석 알림 발송
  - **노쇼 제한**: 노쇼 **누적 2회** 시 클리닉 신청 **영구 제한**(관리자 수동 해제). 노쇼 시 학생·학부모에게 경고 알림

#### 3.2.5 교재 구매
- **결정 사항**: 결제선생 연동/임베드 방식(추후 PG 직접 연동 가능성). **학생·학부모 양측 모두 결제 가능하며 중복은 sync로 차단**(3.1.5)
- **요구사항**: 학생 또는 학부모가 LMS 내 결제선생 연동 화면을 통해 교재 구매/결제를 진행(외부 사이트로 완전히 이탈하지 않고 LMS 흐름 내 진행). 내 결제/배부 상태를 소비자 화면에서도 확인

### 3.3 공통 기능

#### 3.3.1 게시판
- **결정 사항**: 게시판을 다음 카테고리로 운영. 학생·학부모 모두 열람(작성 권한은 카테고리별 상이)
  - **공지사항 게시판**: 관리자 작성. 주차 공지는 캘린더 홈(3.2.0)과 연동
  - **질답(질문답변) 게시판**: 학생이 (주로 학습) 질문을 올리고 강사/관리자가 답변. (3.3.2 문의와 **통합해 단일 창구로 운영** — 8-11 결정. 추후 공개 Q&A/1:1 분리 여지) **공개 방식(2026-07-22 결정): 기본 공개 + 작성 시 비밀글 옵션**(비밀글은 작성자·관리자만 열람 — 결제 등 개인적 문의용)
  - **교재 정오표 게시판**: 관리자 작성
  - **자유게시판(신설)**: 한종철 강사가 짧은 글을 시간순 피드로 자유롭게 올리는 **비학습 친근 소통 공간(트위터형)**. 오프라인 대면의 친근함을 온라인에서 재현하는 차별화·유대 요소. 작성은 강사/지정 관리자
  - **이벤트/굿즈 게시판(신설)**: 오프라인 학생 대상. 관리자가 굿즈 이벤트·배포 소식을 공지하고, 학생이 원하는 굿즈를 요청/제안

#### 3.3.2 문의 (구 "톡 문의")
- **As-is**: 카카오톡을 통한 상담
- **결정 사항**: 카카오톡 연동 대신 LMS 자체 채팅/게시판 기능으로 대체
- **요구사항**: 학생·학부모가 LMS 내에서 문의를 등록하고 관리자가 답변. (질답과 **통합된 단일 창구**로 운영 — 8-11 결정. 추후 공개/1:1 분리 가능)

#### 3.3.3 랜딩 페이지 (비로그인)
- **결정 사항(목적 재정의)**: 로그인 이전 비로그인 방문자를 **잠재 고객**(수업 선택을 고민 중이거나 설명회를 듣고 검색해 유입)으로 정의하고, 이들을 실제 **등록으로 전환**시키는 것을 1차 목적으로 함(매우 중요). 강사(한종철) 소개는 전환을 뒷받침하는 하위 구성요소로 포함
- **요구사항**
  - **어필 내용**: 학원의 차별화된 관리(결석생 직접 관리·시험 분석/약점체크 등)를 설명회 어필 내용과 일관되게 전달해 신뢰 형성 (실제 구현 기능과 일치시켜 과대광고 방지)
  - **디자인 방향**: 조악함 배제, 고급스럽고 세련되며 '관리·홍보가 잘 된' 인상. 올드하지 않고 최신 웹서비스 수준 UI 지향(참고: 토스(Toss) UI). 정보성 콘텐츠가 있어도 시각적으로 끌리게
  - **시즌 팝업/체험(검토)**: 방문자 호기심 유발을 위한 시즌성 팝업. 예: 모의고사 시즌에 본인 성적을 입력하면 분석 예시를 체험(구체 시나리오·연동 범위 미확정)
  - **구성 요소 후보(미확정, 담당 정리 예정)**: ①게시판 일부 공개(공지/정오표), ②강사 사진, ③커리큘럼 소개
  - **UI 디자이너 협업**: UI 디자인은 개발과 별개 전문 영역으로 보고 협업 검토, 필요 시 외부 전문가 섭외
  - **일정/우선순위**: 랜딩에 들어갈 정보·구성은 **2026년 7월 마지막 주까지 확정**. 랜딩과 LMS 동시 오픈 시 **LMS 본체 개발 우선**(랜딩 후순위)

### 3.4 학부모 기능 (신설)
- **결정 사항(6-2 변경)**: 학부모 전용 계정을 1차 범위에 포함. 학부모는 학생과 별도 계정으로 로그인
- **요구사항**
  - **자녀 연동(1:N)·드롭다운**: 한 학부모 계정은 복수 자녀(학생)와 1:N 연동. 자녀 2인 이상이면 화면 상단에 **자녀 선택 드롭다운**을 제공하고, 선택된 자녀 기준으로 성적·출결·결제·보강 신청 등 모든 조회·액션 컨텍스트가 전환. 자녀 1인이면 드롭다운 숨김
  - **조회(읽기 전용)**: 자녀의 성적·출결·결제 상태·캘린더 홈을 조회
  - **액션(신청)**: 결석 동영상 보강(동보) 신청(3.2.3), 교재 결제(3.1.5), 상담/문의 신청(3.1.9·3.3.2)
  - **권한 경계**: 성적·출결 등 데이터 수정 권한은 없음. (허용 write 범위의 세부 경계는 미결 8-12)
  - 계정·초기 비밀번호는 학생과 동일하게 일괄 생성·문자(SMS) 발송(3.1.5)

## 4. 비기능 요구사항 (확정)

- **인증·권한**: 역할 기반 접근제어(RBAC) — 대표·관리자·조교·등록생·미등록(예비등록생)·퇴원·**학부모**. **로그인 진입점은 학생용·학부모용·관리자용 3종으로 분리**(각각 별도 페이지, 역할군만 인증, 성공 시 역할별 홈으로 라우팅). URL은 단일 도메인 + 경로 분리(`/student/*`·`/parent/*`·`/admin/*`). 신규생·학부모 계정은 자동 발급(아이디 = 본인 휴대폰 번호[8-4], 비밀번호 랜덤·변경 가능, 문자 발송). 명단 입력 시 전원 미등록이며 1주차 실제 출석 시 관리자가 '등록' 처리 (2장, 3.1.5, 3.1.6, 6-9 참조)
- **직원 기능 권한(2026-07-22 결정)**: 직원(관리자·조교)의 세부 기능 접근은 **기능 키 단위**로 관리한다 — 기능 키 목록은 코드가 정의, 부여는 DB. **역할 프리셋 + 개별 가감** 방식: 관리자/조교에 기본 기능 세트를 깔고, **대표가 관리 화면(체크박스 매트릭스 UI)에서 사람별로 부여/회수**. 강제는 API 레벨, 메뉴는 서버가 내려주는 보유 기능 목록으로 렌더(상태 기반 노출 원칙과 동일 메커니즘). 대표 전용 민감 기능의 범위는 추후 결정(후보: 권한 부여·직원 계정 관리·클리닉 컷값/노쇼 해제·성적 정정 승인·결제 취소/환불 — `.claude/key_considerations.md` 참조)
- **상태 기반 노출 원칙(2026-07-22 대표 요구 — 전 기능 공통)**: 학생·학부모 화면과 API는 **"지금 그 사용자에게 해당되는 것만"** 노출한다.
  - **신규 발급 계정의 첫 로그인은 거의 bare**: 일괄 생성·배포된 계정(예비등록)으로 들어가면 교재 구매 등 최소 기능만 보인다(2장 미등록 권한과 일치)
  - **기능 단위**: 동보 신청은 **결석생에게만**, 클리닉 신청은 **대상자(출석+응시+평균미달)에게만**, 복습영상은 **권한이 지급된 주차만** — 자격이 없으면 그 기능의 존재 자체가 화면에 없다
  - **콘텐츠 단위**: 커리큘럼·주차별 학습계획·주차 공지는 **시작된 주차까지만**(미래 주차 비공개, 관리자 조기 공개 오버라이드 가능)
  - **목적**: 경쟁사가 학생 계정으로 로그인해도 기능 전모·커리큘럼 전체를 열람할 수 없다. 시스템의 전체 모습은 관리자 화면에만 존재
  - **강제 지점은 API 응답 레벨**(프런트 숨김만으로는 무의미). 각 기능 API는 자격 검사를 포함하고, 홈·메뉴 구성도 서버가 내려주는 자격 정보 기반으로 렌더링
- **알림**: 이벤트 알림 발송(성적/영상권한/결제/리포트/클리닉출결/동보/노쇼/상담 등). **알림 채널 추상화**로 현재 카카오 알림톡, 향후 확장·교체 가능 (3.1.2, 6-8)
- **영상 스트리밍**: **(2026-07-21 전환 확정)** 외부 DRM 호스팅(Mux/VdoCipher 중 미정) + LMS 내 임베드 재생, 4K. 신청·승인·안내·만료는 LMS, 권한 부여/회수는 호스팅 API 자동(연동 개발은 후순위 — 3.1.3)
- **결제**: 결제선생 연동/임베드 유지(Provider 인터페이스 추상화로 추후 PG 전환 대비). 학생·학부모 양측 결제 + sync (3.1.5)
- **화상회의**: 클리닉은 구글 미트 유지. LMS는 신청·배정·시간제한 링크·입장 통제·녹음(조교 감독용)·조교 평가표 관리 (6-3)
- **배치 작업**: ①시청 기간(기본 7일) 만료 시 시청 페이지 자동 소멸 + 권한 자동 회수(연동 전에는 관리자 리마인더) ②등록생 명단 입력 시 신규생·학부모 계정을 출석일 1일 전 자동 발급·발송 ③출석 확정 시 복습영상 자동 지급 처리 ④결석생 상담 대기열 자동 생성
- **용량·확장성(2026-07-21 회의)**: 설계 전제는 **최대 동시 사용자 1,000명**(수강생 규모 상한). 트래픽 급증에 대비해 **자동 스케일링 가능한 서버 구성**으로 도입. 이 규모의 서버 비용은 월 20만원 미만 목표(영상 호스팅 비용 별도)
- **견고성/예외 처리(신뢰성)**: 수업 당일 현장에서는 버그 발생 시 즉시 대응이 불가능하므로, **모든 핵심 플로우는 예외·비정상 케이스 처리를 반드시 포함**해 개발한다. 자동 처리가 어려운 예외는 관리자가 수동으로 처리·우회할 수 있는 수단(체크박스, 수동 지정/보정 UI 등)을 제공 (9.6 테스트와 연계)
- **반응형(디바이스별 우선순위)**: 주 사용 디바이스 = **학생·학부모는 아이패드(태블릿, Safari/Chrome)**, **관리자·조교는 데스크탑**(OMR 수동 보정·성적처리·대시보드·수강생 테이블은 넓은 화면 필수). 스마트폰(모바일)도 지원하되 **태블릿·데스크탑을 1순위**로 설계. 단순 축소가 아니라 레이아웃 리플로우(데스크탑 사이드바 ↔ 모바일 바텀탭, 다열 ↔ 단열)로 대응. **터치 환경(아이패드)에는 호버가 없으므로** 캘린더 홈 등 호버 인터랙션에 탭/펼치기 등 터치 대체 수단 필수. (8-3 휴대폰 미사용 학생 접근성과 연계)

### 6-3. 클리닉 화상회의(구글 미트) 검토 체크리스트

**결정**: 자체 WebRTC 배포 대신 **구글 미트(Google Meet)를 유지**. LMS는 신청·배정·링크 관리·입장 통제·녹음 관리를 담당.

| 구분 | 항목 | 비고 |
|---|---|---|
| 연동 | 미트 링크 생성 | **→ 확정(2026-07-17)**: Calendar/Meet API로 **LMS가 자동 생성**. 서비스계정 도메인 위임(DWD)으로 서버측 처리. **클리닉 1건 = 새 스페이스 1개**(링크 재사용 시 이전 참석자 재입장 가능 — 구글 공식 경고) |
| 기능 | 시간제한 링크 노출 | 시작 5분 전부터 해당 학생 계정에만 노출 — LMS 접근 제어 |

## 7. 참고: 현재 업무 진행 Flow (As-is)

**(1) 오프라인 성적 처리 및 성적표 배부** (아카플로우): OMR 수합 → 온라인 채점 → 알림톡 발송 → 개인별 누적 성적표 인쇄·배부
**(2) 출결 관리** (자체 엑셀): 담임이 출석/결석을 엑셀로 관리, 동보는 누적 표시. 온라인 미공개(연구실 확인용)
**(3) 복습영상 업로드 및 수강** (YouTube): 비공개 업로드 → 카톡 개인별 신청(이름·학원·구글계정) → 해당 계정 공개 전환·엑셀 정리 → 수강 기간 후 다시 비공개
**(4) 교재 결제** (결제선생): 등록생 명단·연락처 수령 → 카톡 청구서 → 결제 확인 후 배부
**(5) 클리닉** (카카오톡 채널 + 구글 미트): 카톡 신청 → 승인 알림톡(미트 링크) → 화상 진행
**(6) 과제물(워크북) 검사** (수기): 조교가 워크북 마지막 페이지에 수기 코멘트·ABC 도장 → 학생이 책으로 수령(학부모 미확인)
**(7) 결석생 상담 / 톡 상담** (전화·카카오톡): 결석 사유 파악·동보 안내 등 (기록 미체계화)

## 9. 운영·인프라·일정·리스크 (신설)

### 9.0 확정 기술 스택
- **프론트**: React SPA (배포 Vercel 또는 Cloudflare Pages 검토 — 학원=상업이라 Vercel 유료/약관 유의, 비용·일관성 시 CF Pages)
- **백엔드**: **Django + DRF**(React용 REST API), Django Admin(내부 운영툴), auth+RBAC. 백엔드 프레임워크로 FastAPI 대신 Django 선택(관리 화면·RBAC·ORM·유지보수성 이점)
- **DB**: **PostgreSQL** (Fly Managed Postgres, 도쿄 리전). 설계는 `db/lms-db-design-2026-07-15.md`
- **비동기/배치**: **Celery** + Celery beat(상시 워커). 계정 자동발급·영상 만료 리마인더·알림 발송·OMR/유사문항 무거운 처리·약점체크 PDF 생성
- **캐시/브로커**: **Redis (Upstash)**
- **오브젝트 스토리지**: **Fly Tigris**(S3 호환, egress 무료) 또는 Cloudflare R2 — OMR 스캔·워크북 사진·클리닉 녹음·PDF (DB엔 경로만)
- **배포**: **Fly.io 도쿄(nrt)**. 수업 시간대 웜 유지(min≥1), 유휴 시 scale-to-zero
- **모니터링**: **Sentry**(에러 트래킹·AI 원인 분석) + Fly 메트릭/로그

### 9.1 모니터링/관측성
- 에러 트래킹·로그 수집·성능/가동상태 모니터링을 광범위하게 도입. 발생 오류의 원인·수정 방향을 자동 분석·설명하는 **AI 기반 진단 도구** 도입(현장 대응 불가 상황 대비, 추가 구독비 감수)

### 9.2 외부 상용 서비스 연계
- **채널톡 도입 방향 결정(2026-07-21 회의, 대표 최종 컨펌 전제)**: 카카오톡·웹사이트·인스타그램 상담 문의를 **한 화면에서 통합 관리**하고 전화 기능(발신·기록)까지 사용. 결석생 전화 상담의 통화 이력·기록이 근거. LMS는 데이터 연동(발신 이력 수집·상담 기록 연결)만 담당
- 알림톡 **직접 발송(트랜잭션 알림)은 채널톡과 별개** — 채널톡은 캠페인 발송만 지원하므로 발송 API는 별도 업체(솔라피 검토, `../local/sources/decisions/2026-07-20-외부서비스-결정.pdf`)

### 9.3 자체개발 vs 외부 API 판단
- 기능별로 비용·개발기간·유지보수 부담 기준으로 선택(예: 통화·상담→채널톡, 알림톡 발송→솔라피 검토, 영상→외부 DRM 호스팅[6-7], 결제→결제선생)

### 9.4 월 운영비용(개략)
- 항목: ①카카오 알림톡 발송비 ②Fly.io 서버·MPG·Redis ③오브젝트 스토리지 ④상용 구독(Sentry/AI 진단·채널톡) ⑤프론트 호스팅
- 방침: 초기 투자 규모는 억대 수준 아님. 현행 대비 월 운영비 다소 증가 수용하되, 항목 도입 시 월 비용 산정·합의. 사용량 기반 서비스는 상한/알림 설정

- 빠른 구현 후 **매일 전 기능·전 케이스 전수 테스트**로 현장 배포 전 버그 제거(오픈 직전·직후 집중 테스트). 자동화 테스트 병행 여부 검토. 모니터링(9.1)과 연계해 발견 오류 최우선 처리

### 9.7 유지보수·인력 리스크
- 단일 개발자 의존 리스크 완화를 위해 제작 과정을 제3자(도훈 컴퍼니)가 병행 파악하여 **백업/유지보수 대비 인력** 확보
- 담당 개발자(지섭)의 목표는 '전 기능 완성'이 아니라 ①제작 과정 책임 ②추후 유지보수 가능한 구조·문서화 ③필요 시 다른 개발자와 협업 가능한 상태. 코드·구조를 인수인계 가능하게 관리

### 9.8 저장소/코드 구조(검토)
