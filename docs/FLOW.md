# FLOW — 제품 전체 흐름 (canon)

> **작성 중.** 대표가 구술하고 정리하는 중이며, 여기 적힌 것이 **기준(canon)** 이다.
> PRD 와 어긋나면 **이 문서가 맞다** — PRD 를 여기에 맞춰 고친다.
> 확정된 단발 결정은 `docs/decisions.md`, 무엇을 만들 것인가는 `docs/PRD.md`,
> **어떻게 흘러가는가는 여기다.**
>
> 시작: 2026-08-12

## 이 문서의 상태 — 읽기 전에

| | |
|---|---|
| **1. 수업 생성** | 적혀 있음. 열린 질문 1건(줄이기와 기존 기록) |
| **2. 학생 등록** | **다시 쓰는 중.** 지금은 엑셀 읽기까지. 옛 판은 아래 접어 뒀다 |
| **3 이후** | **아직 없다** — 수업 진행에 속하는 것은 "나중 섹션 몫" 에 모아 둔다 |

**결제선생 · OMR · 출결 · 계정 생성은 대표가 다시 정리해서 준다**(2026-08-12,
"다음주에 할게"). 그때까지 **여기 적힌 것 이상을 추측해 만들지 말 것** — 특히 2번은
하루 사이에 두 번 뒤집혔다(대조키로 솎아내다 → 전체 번호 판정으로, `id_check` 도입 →
폐기). 지금 형태도 최종이 아닐 수 있다.

**아직 코드는 손대지 않았다.** 이 문서는 설계이고, 마지막 절이 현재 스키마와의 차이를
정리한다. 구현을 시작하려면 대표 확인을 먼저 받을 것.

## 1. 수업 생성

첫 수업을 열기까지의 일이다. **만드는 단위는 `반`** 이고, 반 하나가 곧 하나의 수업 묶음이며 자기 일정을 갖는다.

---

### 1-1. 다섯 층

```
과목구분        수능 · 내신
  └ 과목        통합과학
      └ 커리    2026 여름 N제        ← 무엇을 가르치는가
          ├ 반  목 6.5 대치러셀      ← 언제·어디서 누구에게
          └ 반  화 6.5 대치러셀
               └ 학생
```

| | 담는 것 |
|---|---|
| **커리** | 가르치는 내용. 주차와 그 주차의 영상, 총주차 |
| **반** | 그것을 **언제·어디서 누구에게** 하는가. 개강일·요일·장소·학생 |

**학생 ↔ 반은 N:M 이다.** 수능 반과 내신 반을 같이 듣는 학생이 있을 수도 있다.

---

### 1-2. 기본형 — 아무것도 어긋나지 않을 때

**대칭이 맞는다.** 이게 정상이고 대부분이다.

```
커리  2026 여름 N제   1주차   2주차   3주차  …  10주차     ← 내용 · 영상
                        │       │       │         │
반 목 6.5               9/4    9/11    9/18   …  11/6      ← 주 1회, 번호대로
반 화 6.5               9/2     9/9    9/16   …  11/4
```

- 반은 커리의 주차를 **번호 그대로** 따라간다 — 반 3주차는 커리 3주차다
- **주 1회**다. 주차와 수업 회차가 1:1 이다
- 반 3주차에는 **커리 3주차 영상**이 나간다
- 반은 커리의 **전부**를 한다 (10주차면 10주차까지)

여기까지면 층을 나눌 것도, 포인터를 둘 것도 없다. **아래는 전부 이 대칭이 깨질 수 있는
자리들이고, 깨지는 방식이 서로 달라서 따로 다룬다.**

---

### 1-3. 무엇을 고르고 무엇을 만드나

| 층 | 넣는 방식 |
|---|---|
| **과목구분** | 드롭다운. **신규 입력 없음** — `수능`·`내신` 둘로 고정 |
| **과목** | 드롭다운. **신규 입력 가능** |
| **커리** | 자유 입력 |
| **반** | 자유 입력 |

**왜 과목만 여나.** 과목은 늘어날 수 있다(지금 넷이지만 고정이 아니다). 구분은 늘어나지
않으므로 잠가 둔다 — 열어 두면 `수능`·`수능(재종)` 같은 표기 흔들림이 생기고, 그게
아래 모든 층의 분류를 오염시킨다.

#### 구분 ↔ 과목

| 구분 | 과목 |
|---|---|
| **수능** | 통합과학 |
| **내신** | 일반선택 생명과학 |
| | 진로선택 생명과학 — 세포와 물질대사 |
| | 진로선택 생명과학 — 생물의 유전 |

#### 입력 항목

| 커리 | | | 반 | |
|---|---|---|---|---|
| **커리명** | `2026 여름 N제` | | **수강반명** | `목 6.5 대치러셀` |
| **총주차** | `10` | | **개강일** | `2026-09-04` |

- **요일은 개강일에서 얻는다** — 따로 받지 않는다. 두 곳에서 받으면 어긋날 수 있고,
  어긋나면 어느 쪽이 맞는지 알 방법이 없다
- **총주차는 반이 받지 않는다.** 커리 것이다 — 반이 각자 들고 있으면 커리에 주차를
  더할 때 하위 반을 전부 따라 고쳐야 한다. `2026 여름 N제` 라는 물건 자체가
  "10주짜리 내용 묶음" 이라 길이가 그 물건의 속성이기도 하다

#### 커리와 반을 한 화면에서 만든다

커리를 만들고 그 밑에 반을 만드는 것이 **한 화면에서 끝난다.** 커리만 있고 반이 없는
상태는 쓸모가 없기 때문이다 — 아무도 그 수업을 듣지 않는다. 이미 있는 커리에 반을
더하는 것도 같은 화면에서 된다.

---

### 1-4. 대칭이 깨질 수 있는 자리 ①  — 날짜가 밀릴 수 있다

휴강이 **생길 수 있다.** 그때 어떻게 되는가.

| | |
|---|---|
| **(가) 채택** | `3주차`는 계속 `3주차`이고 **날짜만** 뒤로 간다 |
| ~~(나) 기각~~ | ~~그 주를 비우고 다음 수업이 4주차가 된다~~ |

**왜 번호를 고정했나.** 출결·영상 권한·클리닉이 **전부 주차 번호에 매달려 있다.**
번호가 흔들리면 *이미 쌓인 기록의 뜻이 바뀐다* — 어제 "3주차 결석" 으로 남긴 것이
오늘 다른 수업을 가리키게 된다.

**미는 것은 반 단위다.** 화반이 밀려도 목반은 그대로다. 그래서 일정이 반에 있어야 한다.

**뒤 주차가 따라 밀린다.** 3주차를 11/5 → 11/12 로 밀면 4~10주차도 함께 일주일 밀리고,
**종강일이 그만큼 늦어진다.** 휴강은 "그 주를 건너뛴다" 가 아니라 "그 주부터 전부
한 주씩 늦춘다" 이기 때문이다.

---

### 1-5. 대칭이 깨질 수 있는 자리 ②  — 반마다 끝나는 곳이 다를 수 있다

한 커리 안에서 **10주차까지 가는 반, 9주차에서 끝나는 반, 8주차에서 끝나는 반이
공존할 수 있다.**

그래서 **밀기 · 늘리기 · 줄이기가 서로 다른 동작**이다. 어디서 하는 일인지가 다르고,
다른 반에 미치는 영향도 다르다.

| | 어디서 | 무엇이 바뀌나 | 다른 반은 |
|---|---|---|---|
| **밀기** | **반** | 날짜만 뒤로. 주차 수는 그대로 | 영향 없음 |
| **늘리기(주차 추가)** | **커리** | 주차가 하나 늘어난다 | **다 같이 늘어난다** |
| **줄이기** | **반** | 이 반만 일찍 끝낸다 | 영향 없음 |

**기록이 있는 주차는 못 줄인다.** 출결이 찍혔거나 영상 권한이 나갔으면 그 주차를 잘라
낼 수 없다. 줄이기는 아직 안 한 주차에만 쓴다.

**반은 커리보다 더 가지 않는다.** 11주차가 필요하면 **커리에 더하는** 것이고, 그러면
하위 반 전체에 그 주차가 생긴다. 생긴 뒤의 날짜는 반마다 다르다 — 밀려 있던 반은
그만큼 늦게 한다.

```
커리에 11주차 추가
  반 목 6.5 (안 밀림)     11주차 → 11/13
  반 화 6.5 (한 주 밀림)  11주차 → 11/18    ← 같은 주차, 다른 날
```

즉 **반은 커리의 주차를 덜 쓸 수는 있어도 넘어설 수는 없다.**

#### 반의 주차는 따로 보관한다

커리의 총주차와 별개로 **반이 자기 주차를 갖는다.** "지금 몇 주차인지" 는 수업이
지날 때마다 자동으로 오른다.

| | |
|---|---|
| **밀림** | 여기가 중요하다. 날짜가 뒤로 가도 번호는 그대로여야 기록이 안 흔들린다 |
| 줄임 | 부수적이다. 기록이 있는 주차는 못 줄이므로 실제로는 끝을 앞당기는 것뿐이다 |

---

### 1-6. 대칭이 깨질 수 있는 자리 ③  — 어느 영상이 나갈지 바뀔 수 있다

주차가 줄거나 밀린 반은 **진도를 당겨올 수 있다.** 그래서 `N주차 → N주차 영상` 이
기본값이되 고정은 아니다.

**그리고 한 주차의 영상은 하나가 아니다 — 애초에 n개다.**

```
기본      반 3주차  →  커리 3주차 영상들
당겨오기  반 3주차  →  커리 4주차 영상들      ← 한 주 줄어 진도를 당겼다
섞기      반 3주차  →  3주차 2개 + 4주차 1개   ← 개별로 고를 수 있어야 한다
```

> 포인터는 **번호로 고정된 것이 아니라 고칠 수 있는 목록**이다.
> 반 3주차가 반드시 커리 3주차를 가리키지 않고, 하나만 가리키지도 않는다.

**바뀌지 않는 것은 영상의 정체다.** 업로드 때 "이건 2026 여름 N제 3주차 강의다" 로
못박고 그건 안 움직인다. 바뀌는 것은 *반의 주차가 그중 무엇을 내보내는가* 다.

---

### 1-7. 영상은 커리의 일이다 — 관리자 화면이 이 축으로 갈린다

| 축 | 무엇 | 왜 |
|---|---|---|
| **커리의 일** | **영상** | 내용이라 그 커리를 듣는 반이 다 같이 쓴다 |
| **반의 일** | **출결 · OMR · 클리닉 · 메시징** | 누가 왔고 누가 결석했는지는 반마다 다르다 |

영상만 결이 다르다. 나머지는 전부 "이 반에서 오늘 무슨 일이 있었나" 인데, 영상은
"이 커리의 3주차 강의" 라서 반과 무관하다. **한 화면에 섞으면 두 질문이 섞인다.**

#### 매주 올리고, 올릴 때 자리를 못박는다

한꺼번에 올리지 않는다. **매주 찍어서 매주 올리고, 올릴 때마다 어느 커리의 몇 주차인지
지정한다.** 나가는 것은 자동이다 — 올려 두면 조건이 맞는 학생에게 저절로 열린다.

#### 권한은 반에서 나온다

영상 자체는 커리 것이지만 **누가 볼 수 있는가**는 출결이 정한다(출석 확정 → 그 시점
공개된 그 주 영상에 권한). 즉 **내용은 커리 축, 권한은 반 축**이고, 영상 권한이
두 축이 만나는 자리다.

#### 지금 코드는 이 부분이 이미 가깝다

`videos.Video` 가 `course_week` 를 가리키고(내용 = 주차), `VideoGrant` 는 `attendance`
에서 나온다(권한 = 출결). **축은 이미 갈려 있다.** 한 주차에 영상이 여럿 붙는 것도
FK 라 이미 되고, 지급도 `published_videos_of(course_week)` 로 복수를 전제한다.

빠진 것은 **주차가 매달릴 커리 층**과, **반이 그중 무엇을 내보낼지 고르는 자리**다.

---

### 1-8. 잠금 — 무엇이 언제까지 고쳐지나

> **개강 전에는 다 고칠 수 있다.
> 개강일이 지나면 반의 정체성은 잠기고, 일정만 움직인다.**

| | 개강 전 | 개강 후 |
|---|---|---|
| 구분 · 과목 | 수정 | **잠김** |
| 수강반명 | 수정 | **잠김** |
| 개강일 | 수정 | **잠김** |
| 커리 총주차 | 수정 | **늘린다**(하위 반 전체에 전파) |
| 이 반이 어디까지 | 수정 | **줄인다**(이 반만 · 기록 없는 주차만) |
| 주차 날짜 | — | **민다** (뒤가 따라옴) |

**왜 개강일이 기준인가.** 개강 전에는 아직 아무 기록도 없다 — 고쳐도 잃을 것이 없다.
첫 수업이 지나는 순간부터 출결·권한이 쌓이기 시작하고, 그때부터 정체성을 바꾸면
그 기록들이 무엇에 대한 것인지 모호해진다.

#### 이름을 잠그면 표기 문제가 사라진다

반 이름이 개강 후에 안 바뀌므로 **"지난 출결에 찍힌 반 이름은 옛 것인가 새 것인가"** 를
정할 필요가 없다. 그래서 이름은 **복사하지 않고 참조만 한다.**

지금은 문자열로 두 군데(`CourseEnrollment.class_name`·`Student.current_class`)에
복사돼 있고, 그래서 학생 명부 검색이 `icontains` 부분일치다
(`student_directory.py` 주석: *"반 이름 표기 흔들림 허용"* — 이미 흔들리고 있다는 자백이다).

---

### 1-9. 교재 — 커리에 붙고, 낱개로 등록한다

**교재는 커리에 붙는다. 반별 교재는 없다.** 같은 커리를 듣는 반은 같은 교재를 쓴다.

#### 묶음도 있고 낱개도 있다

**둘 다 등록한다.** 세트가 하나의 상품이고, 그 안의 권들도 각각 상품이다.

```
2026 여름 N제 세트    세트    ← 상품
N제 1권               낱개    ← 상품
N제 2권               낱개    ← 상품
N제 3권               낱개    ← 상품
```

**왜 둘 다인가.** 대부분은 세트로 산다. 그런데 **1권을 이미 갖고 있는 학생**이 있고,
그 학생에게는 나머지 2권만 청구해야 한다. 세트만 등록하면 그 청구를 만들 수 없고,
낱개만 등록하면 세트로 사는 대부분이 세 줄로 쪼개진다.

#### 포함 관계는 DB 에 넣지 않는다

세트가 어느 권을 품는지 **모델로 만들지 않는다.** 상품에 `세트`·`낱개` 표시만 둔다.

**조교가 세트에 무엇이 들었는지 안다는 것을 전제**한다. 청구를 만드는 사람이 사람이고,
그 사람이 이미 아는 것을 시스템에 또 적게 하는 값이 관계를 유지하는 값보다 크다.

**감수하는 것**: 세트와 그 안의 낱권을 같이 청구해도 **시스템이 막지 않는다.**
한 권을 두 번 받는 일은 사람이 걸러야 한다.

#### 교재가 갖는 것

| | |
|---|---|
| 이름 | |
| 가격 | |
| **표지 사진** | 버킷 `edujc-lms-media` 에 올린다 |
| Active | 판매 종료를 삭제가 아니라 끄기로 (주문 이력이 참조하므로) |

**표지 사진을 두는 이유**는 나중에 **학생이 직접 교재를 신청**할 수 있게 하기 위해서다.
고르는 화면에 이름만 있으면 무엇인지 알기 어렵다.

#### 새 모델을 만들지 않는다

`payments.Product` 가 이름·가격·`is_active` 를 이미 갖고 있다. 더할 것은 **표지 사진
한 칸과 커리 연결**뿐이다. `is_active=false` 로 끄는 방식도 이미 그 모델의 계약이다 —
주문 이력이 참조하므로 실삭제를 막아 둔 자리다.

(사진 저장은 이미 선다 — 2026-08-12 에 Tigris 버킷을 붙였고 운영에서 쓰기·읽기를
확인했다. 비공개 버킷이라 URL 에 서명이 붙는다.)

없음.

## 2. 학생 등록

### 2-1. 명단이 온다

**수업 시작 1주일 전**(또는 정해진 기간 전) 학원에서 엑셀을 받는다.

| 이름 | 학교 | 학년 | 학생 핸드폰 | 학부모 핸드폰 |
|---|---|---|---|---|

**조교가 반을 골라서 등록한다.** 파일 자체에는 어느 반인지 우리 시스템과 매핑되지 않을 수 있다.

---

### 2-2. 이 단계의 진짜 문제 — 엑셀이 제멋대로다

우리가 만든 서식이 아니라 **학원이 주는 파일**이다. 같은 뜻인데 매번 다르게 온다.

| 흔들리는 것 | 예 |
|---|---|
| **컬럼 이름** | `이름` · `학생이름` · `성명` / `학생 핸드폰` · `학생HP` · `학생 연락처` |
| **띄어쓰기** | `학부모 HP` · `학부모HP` · `학부모  HP` |
| **컬럼 위치** | 1열에서 시작할 수도, 3열에서 시작할 수도 |
| **학교 표기** | `숙명고` · `숙명여고` · `숙대부속고등학교` · `숙명 여고` |
| **한글 인코딩** | 눈에 같아 보여도 자모가 분리돼 온 값이 섞인다 |

> **여기를 못 넘기면 나머지가 다 막힌다.** 파일을 못 읽으면 계정도 청구도 시작되지 않는다.

---

### 2-3. 최대한 자동으로 잡되, 모르면 사람에게 묻는다

세 겹으로 간다.

```
① 정규화     한글 유니코드 정규화(NFC) · 공백 제거 · 대소문자
                 → 눈에 같은 값이 실제로 같아진다

② 별칭표     알고 있는 변형은 자동으로 맞춘다
                 컬럼: 학생이름·성명·이름  →  이름
                 학교: 숙명여고·숙대부속고등학교  →  숙명여자고등학교

③ 사람       모르는 것이 나오면 조교에게 묻고, 답을 별칭표에 넣는다
                 → 다음부터는 ②에서 자동으로 잡힌다
```

**③이 핵심이다.** 변형을 미리 다 알 수는 없다. 알아서 배우게 만드는 것이 목표고,
조교가 한 번 답한 것은 **다시 묻지 않는다.**

#### 조교가 답하는 두 가지

| 무엇이 낯설 때 | 조교가 하는 일 |
|---|---|
| **컬럼 이름을 모른다** | "이 열은 무엇입니까" → 학생 핸드폰으로 지정 |
| **학교 이름을 모른다** | 새 학교로 등록하거나, 기존 학교의 **다른 이름**으로 붙인다 |

#### 학교는 대표 이름 하나에 별칭이 여럿

```
숙명여자고등학교          ← 대표 이름 (저장은 이것으로)
  ├ 숙명고
  ├ 숙명여고
  ├ 숙대부속고등학교
  └ 숙명 여고
```

**왜 필요한가.** 표기가 흔들린 채로 저장하면 학교별로 세는 것이 전부 갈린다 —
같은 학교가 넷으로 보인다.

#### 컬럼 위치는 이름으로 찾는다

몇 번째 열인지 고정하지 않는다. **머리글 줄을 찾아 이름으로 맞춘다.**
머리글이 1행이 아니라 3행에서 시작할 수도 있으므로 **위쪽 빈 줄·제목 줄을 건너뛴다.**

---

### 2-4. 시스템이 만드는 두 값 — 대조키와 아이디

```
대조키   {이름}{전화 뒷4자리}       김민준1234    겹칠 수 있다   지면(OMR·워크북)이 쓴다
아이디   대조키 + a·b·c·d           김민준1234b   유일          로그인이 쓴다 (= 원번)
```

- **뒷4자리는 학생 번호**, 없으면 **학부모 번호**를 쓴다
- **아이디가 시스템상 원번**이다. 둘은 같은 값이다
- 이름+전화가 겹치면 **다음 사람부터** `a`·`b`·`c`·`d` 를 붙인다
- **`p` 는 접미사로 쓰지 않는다** — `{학생 아이디}p` 가 학부모 자리이기 때문이다

#### 학부모

**학부모 아이디는 학생 아이디에 `p`** 를 붙인다.

**학부모 번호가 이미 있는 번호면 조교에게 묻는다.** 형제일 수도 있고, 남의 번호를
잘못 적었을 수도 있다. 형제가 맞으면 **먼저 만들어진 학부모 계정에 n번째 학생이 붙는다**
— 새 학부모 계정을 만들지 않는다.

**학부모 ↔ 학생은 1:N 이다.**

---

### 2-5. 같은 엑셀이 여러 번 들어올 수 있다

시스템은 같은 반에 엑셀을 **여러 번** 받는다.

**다섯 값 중 하나라도 다르면 다른 학생으로 본다** — 이름 · 학년 · 학교 ·
학생 전화번호 · 학부모 전화번호.

오타로 한 글자가 달라도 **새 학생이 생긴다.** 그건 어쩔 수 없다.

#### 그래서 3개 이상 겹치면 묻는다

완전히 같지는 않은데 **다섯 중 3개 이상이 같으면** 그냥 만들지 않고 조교에게 묻는다.

```
"이런 학생이 있습니다 — 새로 만드는 게 아니라 수정해야 하는 것 아닐까요?"
```

**고치는 방법**은 이렇다: 잘못 생긴 두 번째 학생을 지우고, **첫 번째 학생의 오타를
고친다.** 새로 만든 쪽을 살리는 것이 아니다 — 첫 번째에 이미 기록이 붙어 있을 수 있다.

**오타가 두 군데 이상이면 못 잡는다.** 겹치는 값이 3개 미만이 되어 다른 사람으로
보이기 때문이다. 그건 나중에 손으로 합쳐야 한다.

---

### 2-6. 남은 질문

- **"기간 전"이 정확히 언제인가** — 1주일 전이 규칙인가, 그때그때인가
- 조교가 지정한 컬럼 매핑을 **학원별로 기억할지** — 같은 학원은 매번 같은 서식으로
  줄 가능성이 높다
- 별칭을 **잘못 붙였을 때 되돌리는 길** — 한 번 붙으면 그 뒤 파일이 전부 그리로 간다

### 영상 부여·회수 시점

한 반의 학생은 **같은 시점에 함께 받는다**(동보 제외).

| | |
|---|---|
| 부여 | 그 반의 수업이 끝나고 정해진 시간 뒤 (예: 2시간) |
| 회수 | 다음 주 수업 전 |

- **실제 값은 미정** — 대표가 정한다
- 기준은 **그 반의 수업 시각**이지 달력 시각이 아니다. 반마다 요일·시간이 다르다
- **동보는 해당하지 않는다** — 결석자가 따로 받는 것이라 시점이 개인별이다

### [옛] 학생 등록

반에 학생을 넣는 일이다. **입력은 표 한 장**이고, 그 표에서 계정과 알림이 나온다.

---

### 2-1. 기본형 — 명단이 한 번 깨끗하게 들어올 때

| 이름 | 학교 | 학년 | 학부모HP | 학생HP |
|---|---|---|---|---|

반 단위로 받는다. 넣으면 이 순서로 일어난다.

```
① 학생 계정 생성        아이디 · 비밀번호 · 대조키
② 학부모 계정 생성      없으면 만들고, 있으면 자녀만 잇는다
③ 알림톡 발송           계정 정보
④ 반에 수강 추가
```

**계정과 수강은 다른 판단이다.** ①②가 "이 사람이 있나", ④가 "이 반에 있나" 이고
서로 독립이다. 이미 계정이 있는 학생이 다른 반에 등록되면 **알림톡은 안 나가고
수강만 붙는다.**

---

### 2-2. 아이디 · 비밀번호 · 대조키

셋인데 값은 둘이다.

```
대조키   {이름}{뒷4자리}          김민준1234     겹칠 수 있음   지면(OMR·워크북)이 쓴다
아이디   대조키 + a·b·c           김민준1234b    유일          로그인이 쓴다  (= 원번)
```

- **원번과 아이디는 같은 값**이다. 충돌 접미사까지 포함한다
- **대조키는 별개**다. 지면에 접미사를 찍을 칸이 없어 붙이지 않는다.
  그래서 동명이인 + 같은 뒷4자리면 겹치는데, **결함이 아니라 계약**이다
- **뒷4자리는 학생 번호**, 없거나 학부모 번호와 같으면 **학부모 번호**를 쓴다
- 학부모 아이디는 `{학생 아이디}p`. **최초로 연결된 자녀**를 따르고 동생이 등록해도 안 바뀐다

#### 비밀번호

- **랜덤 생성**이고 최초 로그인에 **변경을 강제**한다
  (`0`·`1`·`o`·`l` 을 뺀 8자리 — 받아 적는 사람이 헷갈리지 않게)
- **알림톡 본문에 실어 보낸다**. 평문이 남지만 변경 강제가 안전망이다
- **잊으면 Teacher 가 되돌린다** → 새 랜덤 발급 + 변경 강제. 스스로 복구하는 길은 없다

> **초기 비밀번호를 이름의 해시로 만들지 않는다.** 같은 반 학생이 서로의 것을 계산할 수
> 있게 되고, 알고리즘이 새면 전원이 뚫린다. 되돌림은 새 랜덤 발급으로 한다 —
> 사용자에게는 똑같고 위험만 사라진다.

---

### 2-3. 알림톡이 어디로 가는가

| | |
|---|---|
| **학생 HP 없음** | 학부모 번호로 **두 계정 정보가 다** 간다 |
| **학생 HP 있음** | **각각** 자기 번호로 간다 |

학생 전화번호는 **선택 입력**이다.

---

### 2-4. 학부모 한 명이 자녀 여럿을 갖는다

형제·자매가 있으면 학부모 계정 하나에 학생이 여럿 붙는다.
나중에 **성적을 볼 때 드롭다운으로 자녀를 고른다.**

---

### 2-5. 깨질 수 있는 자리 ①  — 같은 사람이 또 올라올 수 있다

학생은 2주차·3주차에도 **들어올 수 있다.** 그래서 같은 반에 엑셀이 여러 번 올라오고,
같은 파일일 수도 사람이 늘어난 파일일 수도 있다.

```
1차 30명  →  30명 생성 · 30건 청구
2차 32명  →  늘어난 2명만 생성 · 2건 청구   (앞의 30명은 아무 일도 없다)
```

> **업로드는 멱등이어야 한다.** 같은 파일을 두 번 올려서 계정이 두 벌 생기거나
> 청구가 두 번 나가면 안 된다.

#### 같은 사람인지는 세 값 전부로 판정한다

> **(이름, 학생번호, 학부모번호) 셋이 전부 일치해야 같은 사람이다.**
> 하나라도 다르면 다른 사람이고 새 계정이다.

**대조키로 판정하지 않는다** — 뒷4자리만 보므로 너무 헐겁다. 같은 엑셀에 동명이인이
있어도 번호가 다를 것이므로 자동으로 갈라진다.
**대조키는 지면 대조에서만 쓴다.**

**학생번호 == 학부모번호면** 학부모 번호로 보고, 학부모 번호만 있는 경우와 같이 다룬다.

---

### 2-6. 깨질 수 있는 자리 ②  — 애매할 수 있다

셋이 다 일치하지는 않는데 **6자리 이상 비슷한** 사람이 있으면 시스템이 판단하지 않는다.

```
"이런 학생이 있습니다"
   ├ 기존 학생을 수정한다  →  학생 상세로 이동 · 고치고 돌아와 이어서
   └ 새로 만든다           →  그대로 생성
```

**업로드 전체가 "완료" 를 누를 때까지 확정되지 않는다.** 물어보는 동안 큐는 잡혀 있고
**부분 반영이 없다** — 절반만 만들어지고 멈춘 상태가 생기지 않는다.

#### 계정 생성 로직 (전체)

```
① 정규화      학생번호 == 학부모번호 → 학부모 번호만 있는 경우로 처리

② 동일 판정   (이름, 학생번호, 학부모번호) 셋 다 일치?
   ├ 일치     →  같은 사람. 계정 생성 안 함 · 알림톡 안 보냄  →  ⑤
   └ 불일치   →  ③

③ 유사 검사   6자리 이상 겹치는 사람이 있나?
   ├ 있음  →  ⏸ 보류 · 사람이 고른다
   │           ├ 기존 학생 수정  →  학생 상세 → 고치고 돌아옴 → ② 다시
   │           └ 새로 생성       →  ④
   └ 없음  →  ④

④ 계정 생성   대조키 → 아이디(충돌 시 증가) · 랜덤 비밀번호 · 알림톡 발송

⑤ 수강 추가   이 반에 없으면 수강 추가

              ⟶ 전부 "완료" 를 눌러야 확정된다
```

### 2-7. 깨질 수 있는 자리 ③  — 틀리게 올라올 수 있다

전화번호를 잘못 적어 올릴 수 있다. **고치면 아이디가 바뀐다** — 아이디가 뒷4자리에서
나오기 때문이다.

**엑셀을 다시 올려서 고치는 것이 아니라 학생 상세 페이지(2-8)에서 고친다.**

| 틀린 것 | 하는 일 |
|---|---|
| 학생 번호 | 아이디·비밀번호 재생성 → **학생 계정 안내 재발송** |
| 학부모 번호 | 아이디·비밀번호 재생성 → 안내 재발송 **+ 결제선생 청구 재발송** |

학부모 번호가 틀리면 **청구서가 엉뚱한 번호로 갔다는 뜻**이라 청구도 다시 나가야 한다.

**학생 정보(수강 이력·출결·성적)는 그대로 둔다.** 계정을 다시 만드는 것이 아니라
아이디와 비밀번호만 다시 만든다.

> **대조키도 같이 바뀐다.** 다만 **이미 낸 답안지는 그대로 둔다** — 대조는 낼 때 한 번
> 끝난 일이고, 소급해 다시 돌리면 조교가 손으로 고른 것까지 뒤집힌다.

### 2-8. 학생 상세 페이지

2-6 에서 "수정" 을 고르면 오는 곳이고, 학생에 대한 모든 것이 여기 있다.

| | |
|---|---|
| 학교 | |
| **학년** | 아래 승급 규칙 |
| 원본 번호 | 명단에 적혀 온 값 그대로 (학생·학부모 양쪽) |
| 대조키 | 파생값 |

여기서 **전부 고칠 수 있다.**

#### 학년은 3월 1일에 자동으로 오른다

```
예비 고1  →  고1  →  고2  →  고3  →  N수  →  N수 (멈춤)
```

- **중3은 없다** — 전부 `예비 고1` 로 통칭한다
- **N수는 더 오르지 않는다**

#### 대조키가 같은 학생이 한 반에 둘이면 — 자동으로 못 가른다

지면에서 오는 것은 **이름과 뒷4자리가 전부**다. 둘이 같으면 구분할 근거가 없다.

> **자동 매핑을 시도하지 않는다. 매번 사람이 지정한다.**

조교가 고른 것을 기억해 재사용하는 방식(`id_check`)을 검토했다가 **버렸다.**
맞는 경우가 없기 때문이다 — 안 겹치면 애초에 자동이라 기억할 것이 없고, 겹치면
다음 장이 여전히 둘 중 누구인지 모르므로 **두 번째 학생의 답안지가 첫 번째에게
조용히 붙는다.**

계정은 전체 번호로 갈리므로(2-5) 두 사람의 **계정은 갈린다.** 갈리지 않는 것은
지면 대조뿐이고, 그건 종이가 담는 정보의 한계라 코드로 풀 수 없다.

### 2-9. 교재 결제 청구

명단 등록 직후 **결제선생으로 청구가 나간다.**

| | |
|---|---|
| 채널 | 알림톡이 아니라 **결제선생** |
| 시점 | **즉시**. 폴링·배치가 아니라 명단이 등록되는 그 자리에서 |
| 순서 | **첫 수업 전**이고 **출석을 기다리지 않는다**(예비등록 상태여도 나간다) |
| 묶음 | 명단 한 번에 형제가 같이 들어왔으면 **한 건으로** |
| 대상 | 그 커리의 교재 중 **이 학생에게 필요한 것**(1-9 — 낱개 단위) |

**PRD 3.1.5 의 "커리큘럼 시작 첫 수업 기준 1회" 는 틀렸다** — 청구는 그보다 먼저다.

#### 무엇을 청구하는지가 학생마다 다를 수 있다

묶음과 낱개를 둘 다 등록하는 이유가 여기서 살아난다(1-9). 보통은 **세트 한 줄**로
청구하고, 1권을 이미 가진 학생에게만 **낱권 2줄**로 청구한다. 즉 **청구 대상이 커리
단위가 아니라 학생 단위**다.

기본값은 그 커리의 교재 전부이고, 거기서 빼는 식이 된다.

#### 형제 합산은 구조가 필요하다

지금 `Order` 는 **학생 1명 + 교재 1종**이다. 형제 둘이 각각 2권씩이면 주문 4건인데
청구서는 1건이어야 한다 — 청구서가 주문 여럿을 덮는 층이 있어야 한다.

### 2-10. 남은 질문

- **미래탐구·러셀 구분** — 장소가 여럿이다. 반 이름에 섞어 쓰는 지금 방식으로 둘지,
  따로 뺄지 (일주일 전 확실)
- **계정 생성 시점** — 명단이 들어온 즉시인지, 따로 누르는 것인지
- **학교 이름 별칭** — `숙명고`·`숙명여고`·`숙대부속고등학교` 가 같은 학교다.
  표기가 흔들리는 채로 두면 학교별 집계가 갈린다
- **신규 엑셀 포맷** — 지금 표 다섯 칸과 실제로 오는 파일이 다를 수 있다
- **누가 "이 학생은 이 권이 필요 없다" 를 정하나** — 명단에 칸이 오는가, 조교가
  체크하는가, 아니면 일단 전부 청구하고 학생이 빼 달라고 하는가
