# 확정 사항

> 대표와의 대화에서 **결정된 것만** 모은다. PRD 는 제품 요구사항 전체를 서술하는
> 문서라 결정이 문단 속에 묻혀 다시 찾기 어렵다 — 이 파일은 "그래서 뭘로 정했지"에
> 한 줄로 답하는 자리다.
>
> **규칙**
> - 결정된 것만 적는다. 검토 중·후보·아이디어는 여기 오지 않는다(`.claude/to-do.md` 로)
> - 뒤집힌 결정은 지우지 말고 **뒤집혔다고 표시**한다 — 왜 바뀌었는지가 다음 판단의 근거다
> - 각 항목에 **확정일**과 **대표 원문**(있으면)을 남긴다
> - 구현이 이 파일과 어긋나면 **이 파일이 맞다**. 코드를 고친다
>
> 최종 갱신: 2026-08-12

## 1. 식별자

**식별자는 둘, 그리고 지면 대조용 키가 하나다** (2026-08-05 확정).

| | 무엇 | 어디 | 유일한가 |
|---|---|---|---|
| `student_id` | DB PK. 전 도메인 FK 의 대상 | `students` | 예 |
| **원번** = **로그인 아이디** | 학생의 번호이자 로그인 아이디 | `users.login_id` | **예** |
| **대조키** | 지면 대조 **전용** | `students.matching_key` | **아니오** |

**원번은 더 이상 따로 저장하지 않는다.** 예전에는 `students.unique_id` 에 원번을
저장했는데, 충돌 접미사만 빼면 로그인 아이디와 글자까지 같은 값이라 같은 것이
두 이름으로 있었다. 컬럼명이 `unique_id` 인데 계약은 "중복될 수 있다"였던 것도
그 혼선이다. 원문 *"lets actually make login_id = 원번, we dont need two things"*.

남은 컬럼은 **지면 대조 한 가지 일**만 하므로 이름도 `matching_key`(대조키)로 바꿨다.

- **원번 형식**: `{이름}{휴대폰 뒷4}` + 겹치면 접미사 — `김하늘0001` · `김하늘0001a`
- **대조키 형식**: `{이름}{휴대폰 뒷4}`, **접미사 없음** — 지면이 접미사를 못 담기 때문

**충돌 접미사** — `a` `b` `c` … `z` 중 **`p` 제외**(학부모 아이디가 `{학생아이디}p` 라
겹친다). 25개를 넘으면 두 글자로 확장하되 **끝자리가 `p` 인 것은 건너뛴다**
(`pa`·`pb` 는 쓰고 `ap`·`bp` 는 안 쓴다 — `ap` 는 `…a` 학생의 학부모 자리다).

**학부모는 접미사가 없다.** 자녀 아이디에서 파생되므로 자녀가 유일하면 자동으로 유일하다.

> **지면에는 대조키만 온다.** OMR 은 자모·숫자 격자라 접미사를 찍을 칸이 없고,
> 워크북도 **조교가 대조키만 적는다**(2026-08-05 확정). 그래서 대조키가 겹치면
> 후보가 여러 명 뜨고 **조교가 화면에서 고른다** — 인식값은 **"예비값"**이고
> 확정은 사람이 한다.

- **2026-08-05 확정**: 원번 = `login_id` 로 통합, 지면용 컬럼은 대조키로 개명
- ~~2026-07-30: 원번 = 로그인 아이디와 같은 축(값은 따로 저장)~~ → **완결**됨(위)
- ~~2026-07-29: 원번 = `학년+이름+뒷4`~~ → **뒤집힘**(같은 날). 지면에 들어오는 것이 곧
  원번인데 학년을 넣으면 지면과 어긋난다
- ~~2026-07-15 PRD: 원번 = 학년1+전화뒷4 숫자 5자리, **불변**~~ → **뒤집힘**

## 2. 출결

**출석 / 결석 / 결석(동보) / 결석(현보)** — 담임이 직접 찍는다.

- **동보** = 동영상 보강. **현보** = 현장 보강(다른 수업 학생이 우리 수업으로 옴)
- **지각 없음**(2026-07-30). 시험을 **수업 초반**에 보므로 지각하면 OMR 카드가 안
  들어온다 → 성적이 **"시험 미제출"**로 나가는 것으로 드러난다. 출결 값으로 두면
  같은 사실이 두 곳에 갈린다
- **퇴원은 출결 값이 아니다.** 학생 상태(`enrollment_status`)에 한 번만 저장하고,
  출결 화면에서는 명단에 남아 `퇴원` 으로 표시된다. 원문 *"한번에 찍고 그 이후에는
  이미 퇴원함"*. 회차마다 찍게 하면 "3회차는 퇴원인데 5회차는 출석"이 저장된다

## 3. 복습영상(동보)

- **그 수업에 출석한 학생 전원**이 볼 수 있다
- **결석한 학생**은 동보를 신청하면 볼 수 있다
- 시청 권한 **7일 만료**

### 호스팅 — Mux (2026-07-30 확정) · **4K 전제 폐기 (2026-08-04)**

> **촬영 원본이 1080p 다.** 4K 로 올린 줄 알았던 파일을 Mux 자산 정보로 확인하니
> 전부 `resolution_tier: 1080p` 였고, `max_resolution_tier: 2160p` 를 요청해도 HD 가
> 나왔다(Mux 는 업스케일하지 않는다). 대표 확인 후 **1080p 로 확정**.
> 아래 "4K고 무조건 DRM" 중 **4K 부분은 폐기**, DRM 은 유지.
> 등급은 **premium** — 실측상 1080p 비트레이트가 plus 의 1.7배(6.55 vs 3.84 Mbps)이고
> 회선이 나쁠 때 바닥이 270p 가 아니라 360p 다. 판서 글씨가 여기서 갈린다.
> 근거: `docs/2026-08-04-영상호스팅-비용재계산.md`

> ⚠ 아래 수치는 **재계산으로 어긋난 것이 확인됐다** — `docs/2026-08-04-영상호스팅-비용재계산.md`.
> "월 1,600시간"은 원생 133명분(설계 전제 1,000명과 7.5배 차) · "월 11~17만원"은
> 인코딩 상각·라이브러리 스토리지·부가세 10%를 뺀 값(실제 30명에서도 월 33만원).
> **업체 결론(Mux)은 유지되나 현재 규모에선 두 업체 차이가 월 3~6만원이라 가격으로
> 고를 수 없다.** 결정에 필요한 미결 항목은 그 문서 §8.

**4K + DRM 무조건.** 원문 *"4K고 무조건 DRM할거야"*.

| | 값 |
|---|---|
| 연간 녹화 | 100시간 (4K) |
| 예상 월 시청 | 1,600시간 |
| 예상 월 비용 | **11~17만원** |

- 월 1,600시간 = 96,000분으로 **무료 구간 10만 분의 96%** — 여유 4%뿐이고 Mux 는
  버퍼링된 구간도 과금한다. 11만원은 최선의 경우다
- **미확인**: 선불 크레딧($20 → $100)이 DRM 접근료 $100 에 적용되는지. 적용되면
  11만원, 아니면 17만원. Mux 에 직접 물어야 한다
- VdoCipher 는 GB 과금이라 4K 에서 월 55만원 이상 — 4K 가 요건인 이상 탈락
- **DRM 액세스 요청은 런칭 직전에**(2026-07-30 대표: "아직 돈내기 싫어서"). 요청 조건이
  유료 플랜 업그레이드라 그 시점부터 과금이 시작된다. 그 전까지는 무료 계정으로
  재생 품질만 확인한다 — 단 **본 라이브러리는 그때 올리면 안 된다**: 무료 등급(`basic`)에는
  DRM 을 걸 수 없어 `plus` 로 다시 올려야 한다(4K 100시간 재인코딩 약 $600)

#### 채점과 이상은 다른 축이다 (2026-08-12 확정)

`sheet_answers.result` 한 컬럼에 정답·오답·무응답·복수마킹·판독불가가 섞여 있었다.
**둘로 가른다** (대표 지시 *"이슈로 나누는게 아니라 그냥 issue = true"*):

| 컬럼 | 값 | 언제 |
|---|---|---|
| `result` | 정답 · 오답 · **NULL** | 깨끗한 단일 마킹일 때만 채점이 성립한다 |
| `issue_reason` | 무응답 · 복수마킹 · 판독불가 · **NULL** | 조교가 이 줄을 봐야 하는 이유 |

- **`issue` 불리언 컬럼은 두지 않는다.** `issue_reason IS NOT NULL` 과 같은 값이라
  두 벌이면 어긋난다(§6 사본 금지). API 응답에만 `issue: true/false` 로 나간다
- 섞여 있을 때는 "정답률"을 낼 때마다 **무엇을 빼야 하는지 매번 따져야 했다**.
  실제로 `report` 의 비정답 집계가 NULL 을 안 세는 SQL 3값 논리에 걸릴 뻔했다
- **보정 대기는 복수마킹·판독불가만**(`BLOCKING_ISSUES`). 무응답은 학생이 안 푼
  사실이라 표시만 한다 — 넣으면 큐가 무응답으로 덮인다
- 이 변경으로 **매칭은 됐지만 복수마킹 줄이 있는 장**이 처리 상태 `완료` 에서
  `보정필요` 로 옮겨졌다. 예전에는 조교가 고를 줄이 있는데도 그냥 지나갔다

### "시험 봤나"의 단일 원천은 `scores.is_taken` (2026-08-12 확정)

같은 사실이 두 곳에 있었다 — `attendances.exam_taken`(담임이 수업 중에 찍는 값)과
`scores.is_taken`(답안지가 들어왔나). **후자가 진실이다.** 시험을 봤다는 것의
관측 가능한 증거는 답안지고, 담임의 입력은 스캔 전의 예측이다.

- 판정(클리닉 자격·성적표·응시자 수)은 `is_taken` 만 본다
- 배치 판독이 끝나면 **답안지가 안 온 학생의 성적 행을 `is_taken=False` 로 만든다**
  (`scoring.mark_missing`). 그 전에는 시드 말고는 아무도 안 만들어서 **미제출
  학생이 성적 화면에 아예 없었다**
- 명단은 `class_sessions.exam` 으로 매인 회차의 출결에서 온다. 회차가 안 매여
  있으면 아무것도 만들지 않는다 — 누가 봤어야 하는지 알 수 없으므로
- `attendances.exam_taken` 컬럼은 출결 화면이 아직 쓰지만 **판정에는 안 쓴다.**
  제거는 출결 트랙의 몫

### 익명 점수 — 누군지는 안 알리고 점수만 준 학생 (2026-08-12 확정)

조사 카드에 **점수만 있고 성명·번호가 빈 장**이 온다. 대표 원문: *"평균을 내기
위해 점수는 알려줄게 근데 내가 누군지는 안알려주는 학생들"*. 자기보고 지면이라
그럴 수 있고, **그 점수도 기록돼야 한다.**

- **집계에는 들고 학생에는 안 붙는다.** `scores.student` 는 NOT NULL 이라 행을
  만들 수 없다 — 평균·백분위의 **모집단을 낼 때 답안지 쪽에서 끌어온다**
  (`scoring.anonymous_totals`)
- **조교가 확정한 장만 센다**(`is_corrected=true` + 학생 없음). 미확정 장까지
  세면 평균이 먼저 나갔다가 주인을 찾는 순간 바뀐다 — 성적표가 두 번 다른 말을
  한다. 확정은 보정 화면의 버튼이고, 그러면 보정 대기에서도 빠진다. 학생을
  안 고른 장에서는 그 버튼이 **`익명으로 확정`** 으로 바뀐다 — 같은 자리가 두
  가지 뜻을 갖는데 `확인` 만 적혀 있으면 조교가 모르고 누른다
- **백분위 모집단에도 든다.** 빼면 남은 학생들의 백분위가 실제보다 높게 나온다
- 목록의 응시자 수·평균은 상세와 **같은 계약**이다. 시험마다 `summary_stats` 를
  부르면 N+1 이라, 목록은 익명 (수, 합)을 한 쿼리로 끌어와 같은 값을 만든다

### 백분위·석차는 채점이 끝나는 자리마다 다시 낸다 (2026-08-12)

`scores.percentile`·`rank_top_pct` 는 컬럼만 있고 **채우는 코드가 없었다** —
성적표에 영원히 `—` 로 나갔다. `scoring.rank` 가 낸다.

- 백분위 = (내 점수 미만 + 동점 / 2) / 응시 × 100 — 동점을 반씩 나누는 표준
  백분위 순위다. 동점자 둘이 다른 값을 받으면 같은 점수에 다른 등급이 나간다
- 석차 상위 % = 공동 석차 / 응시 × 100
- 한 명의 점수가 바뀌면 전원이 흔들리므로 **시험 단위로 통째로** 다시 낸다
  (업로드·재판독·정답 키 수정·보정 저장)

| | |
|---|---|
| 손글씨 있는 장에서 맞힌 비율 | 42/44 = 95.5% |
| 맞힌 건 신뢰도 | 최소 0.748 · 중앙 0.995 |
| 틀린 건 신뢰도 | 0.617 · 0.890 |
| 0.90 문턱 | 자동 채택 36장 · **오답 0** |

틀린 두 건은 `1` 과 `7` 이었다 — 한국식 7 은 가로줄이 있어 1 과 붙는다.
tesseract 는 같은 표본에서 17% 였다(인쇄 글자용이라 손글씨를 못 읽는다).

**결과(붙인 코드 그대로 94장 재실행)**: 버블 59 + OCR 20 = **79/94(84%)**.
못 읽은 15장 중 12장은 손글씨조차 없는 백지다.

**이름·전화는 OCR 로 보완하지 않는다** (2026-08-12 실측으로 폐기).

격자가 비면 그 위 손글씨 칸으로 채우자는 안. **실물로 재 보고 접었다.** 답안 카드
48장의 격자 판독을 정답 삼아 손글씨 칸을 OCR 에 물렸다:

| | 일치 | 불일치 | 글씨 못 읽음 |
|---|---|---|---|
| 이름 | 26 | 14 | 5 |
| 전화 | **12** | **18** | 14 |

- **신뢰도가 옳고 그름을 못 가른다.** 틀린 전화 판독이 0.999·0.997·0.995 로 왔다.
  문턱을 0.98 에 둬도 채택 15장 중 7장이 오답이라 **세울 문턱이 없다**
- 파싱 문제가 아니다: 44장 중 14장은 숫자를 아예 못 찾았고, 4자리로 온 21장 중
  맞은 것이 12장이다
- **칸별로 잘라도 안 된다** — 전화 0/20, 이름 8/20 으로 오히려 나빠졌다
  (점수칸은 넓은 여백에 숫자 하나라 95.5% 였는데, 신원칸은 점선으로 나뉜 좁은
  칸 넷이라 지면 성격이 다르다)

**정확도보다 위험이 더 큰 이유**: 잘못 읽은 대조키는 "명단에 없음"으로만 떨어지지
않는다 — **다른 실존 학생의 키와 맞을 수 있다.** 그러면 그 장이 조용히 남의
성적이 된다. 신뢰도로 거를 수도 없으니 잡을 방법이 없다.

그래서 OCR 은 **점수칸 하나**로 유지한다. 점수는 틀려도 그 학생의 점수가 틀릴
뿐이고, 조교가 지면과 나란히 보고 고친다.

**자동 등록이 아니다** (2026-08-12 대표 지시 *"근데 이게 자동 등록은 아니고"*).

성명 격자도 비어 있어 학생이 안 붙고(`비정상`), **학생이 없으면 scores 행이 아예
생기지 않는다.** 조교가 지면을 보고 학생을 고른 뒤에야 성적이 된다 — OCR 은
보정 화면에 값을 미리 채워 둘 뿐이다.

버블에서 온 점수인지 손글씨에서 온 점수인지는 `answer_sheets.score_from_handwriting`
이 들고, 보정 화면이 `손글씨` 배지로 가른다 — **값만 보면 구분이 안 되기 때문이다.**
조교가 그 칸을 손대면 플래그는 꺼진다(사람이 적은 값은 더 이상 OCR 판독이 아니다).
- 실측(샘플 65장 전수): 200dpi 8bit 흑백 · A4 가로 카드가 세로 페이지에 90° 누워 들어옴 ·
  네 모서리 정렬 마커 65/65 검출 · 기울기 최대 -3.55° · 배율이 공칭의 0.948배

## 6. 채널톡 — 연동 범위 (2026-08-04 확정)

**LMS 로 끌어오는 것은 전화 이력뿐이다.** 문의 채팅·옴니채널(카톡·인스타)·CRM 은
채널톡 안에만 두고 동기화하지 않는다. 원문 *"일단 전화 빼고 나머지 데이터는 우리 lms로

**이미 아는 길을 여는 일**이라 비용이 낮다. 그래서 지금 좁게 가도 손해가 아니다.

| 고객 프로필(CRM) | 채널톡만 | 없음 |

  (컬럼은 연동 착수 때 판다 — 지금 파면 안 쓰는 칸이다)
- **대가: 안 끌어오는 것에는 백업이 없다.** 채널톡 약관에 미납·해지 시 삭제 조항이 있어

## 7. 랜딩 히어로 — 터치 기기의 규칙 (2026-08-05 확정)

**"첫 입력 전에는 아무 일도 안 일어난다"는 포인터가 있는 기기에만 적용한다.**

대표 원문: *"sure just on mobile we can apply a different rule and change the rule"*

원래 규칙(2026-07-29 확정)은 그대로 살아 있다 — 데스크탑은 열자마자 검정이고 커서를
움직여야 우주가 드러난다. 코드도 한 줄 안 바뀌었다.

**뒤집힌 부분은 터치뿐이다.** 그 규칙이 막으려던 것은 "커서가 거기 있지도 않은데
우주가 열려 있다"였는데, 커서가 없는 기기에는 부재할 커서가 없어 전제가 성립하지
않는다. 전에는 스크롤을 신호로 썼지만 스크롤은 히어로를 **떠나는** 동작이라
클라이맥스가 히어로를 본 뒤에 오고 있었다.

터치에서는 앰비언트 드리프트가 첫 프레임부터 돈다. 열림은 `CFG.wake`(만개 1.7초)로
번지고, 즉시 켜지 않는다 — "번쩍"은 2026-07-29 에 이미 버린 감각이다.

근거(5개 각도 조사, 2026-08-05):
- 커서 연출을 쓰는 곳의 다수는 터치에서 그냥 아무것도 안 한다 — Codrops 저장소
  59개 중 53개가 `touchmove` 미사용, `pointer: coarse` 사용 0건
- 그러나 호버를 터치에서 빼도 되는 조건은 **"호버가 아무것도 새로 공개하지 않을 때"**
  뿐이다(24 ways). 우리는 배경 사진 전체를 공개하므로 그 조건을 못 맞춘다
- 제약(원판 금지·문구 금지·데스크탑 불변)을 다 통과하며 "영영 안 열림"을 푸는 패턴은
  앰비언트 드리프트 하나였다 — trionn.com 이 `(1 - explodeAmt)` 로 쓰고, 같은 효과를
  파는 상용 컴포넌트 Cursor Reveal 이 "touch + idle animation" 을 기본으로 묶어 판다
- **자이로는 배제**했다 — iOS 가 `requestPermission()` 에 사용자 제스처를 요구해
  탭 대상과 안내 문구가 필요해지고, 그 문구가 §8 과 충돌한다
  (three.js 도 `DeviceOrientationControls` 를 PR #22654 로 삭제했다)
- 스크롤 진행도에 묶는 방식은 조사한 사이트 10곳 중 **0곳**이었다

## 9. 비동기 처리 — Celery + Redis (2026-08-12 확정)

**워커를 띄운다.** ~~주기 작업은 supercronic 이 맡는다(2026-08-05)~~ → **뒤집혔다.**

그때 판단의 전제는 *"떠넘길 웹 요청이 없다"* 였다. 이제 있다 — 결제 취소가 요청
안에서 알림을 걸고, 8-17 트리거들이 같은 경로로 붙는다. 브로커가 없으면 **요청
스레드가 알리고 응답을 직접 물고 있어야** 하고, gunicorn 워커가 3개뿐이라 업체가
느려지면 사이트가 통째로 선다.

| | 확정 |
|---|---|
| 브로커 | Upstash Redis, **정액 250MB $10/월** |
| 왜 정액인가 | Celery 는 **큐가 비어도 계속 폴링**한다(Upstash 문서). 종량제로 만들었다가 되돌렸다 |
| 크기 | 250MB 는 **정액제의 최소 등급**이라 고른 것 — 실사용은 **312바이트/키 11개** |
| 워커 | **1대 고정, 512MB.** 실사용 약 220MB 라 256MB 는 OOM |
| beat | **워커 안**(`-B`). 그래서 **워커를 2대로 늘리면 스케줄이 두 번 발행된다** |
| supercronic | **걷어냈다.** 클리닉 수집이 beat 에도 같은 20분 주기로 있어 두 번 돌 뻔했다 |

**한 워커가 전 앱의 태스크를 받는다**(`autodiscover_tasks`) — 트랙마다 워커를 두지
않는다. 지금 등록된 것: 클리닉 감독 수집 · 알림 발송 · 알림 재발송.

비용은 **월 약 $13**(Redis $10 + 워커 $3.2), cron 머신을 없앤 만큼 빼면 **순증 약 $11**.

### 요금제 — 정액 유지 (2026-08-12 실측 후 확정)

유휴 상태로 10.2분 재니 **639 명령 = 초당 1.04회**, 월 환산 **270만 명령**이다.
종량제로 치면 **$5.41/월** 이라 정액보다 $4.6 싸다. **그래도 정액을 유지한다** —
종량제는 사고가 그대로 요금이 된다(워커가 2대로 뜨면 폴링도 2배다. 2026-08-12 에
실제로 그렇게 떴다). 정액은 그 위험이 없다.

**초당 1회의 정체는 `BRPOP` 다**(로컬에서 `MONITOR` 로 확인 — 30초에 29회, 다른
명령 0). 워커가 "일 오면 깨워줘, 없으면 1초 뒤 다시" 로 큐를 지키는 소리이고,
**일이 없어도 계속 나간다**. beat 는 거의 잠들어 있다(주기 작업이 20분·1시간짜리뿐).
줄이려면 그 간격을 늘려야 하는데 **알림이 나가기까지의 지연이 그만큼 늘어난다** —
1초는 그 지연을 1초로 유지하는 값이라 그대로 둔다.

발송량이 늘어도 이 값은 안 변한다. 알림 한 건은 명령 몇 개라 폴링 270만 옆에서는
반올림 오차다 — **이 비용은 트래픽이 아니라 "워커가 켜져 있음"의 값**이다.
